本文为新项目设计。默认方案已选定，执行Agent不得重新比较十套框架后自由替换。发现事实性阻塞时提交简短ADR、最小替代与影响，再继续不受影响任务。

## 2. 核心职责

identity：本地学生会话、管理员权限、偏好。content：课程源、发布版本、课文/资源适龄性。teaching：学习课时、轮次、上下文、动作建议、可解释下一步。assessment：题目快照、提示、答案、确定性判分。learning：事件、证据投影、记忆候选与学生修正。resources：文件登记/任务/校验/供给。codelab：授权任务与运行申请、评分投影；真正执行在runner。

所有HTTP handler先认证/解析，再调用应用服务。所有数据库写入都经过本地服务。Knodo数据与输出不作为数据库授权依据。

## 3. 数据模型（按功能阶段增加，不先铺满）

| 对象 | 关键字段/约束 | 权威与版本 |
|---|---|---|
| user/auth_session | 用户、角色、哈希密码、会话hash/expiry/revoked | 登出可撤销；原始token不落库 |
| learner_profile/preferences | grade可空、stage、偏好、version | 用户可修改；两字段一致性检查 |
| course/chapter | stable_slug、知识点关联、适用范围、状态 | 作者源；未审核不发布 |
| curriculum_release/chapter_revision | release_id、chapter_id、revision、body、source_manifest_hash | 发布不可变；课程修改创建新版本 |
| resource/resource_revision | kind、MIME、size、sha256、storage_key、来源/许可/审核 | 学生只见获准版本 |
| lesson_session | student_id、chapter_revision_id、phase、status、revision | 每个学生独立；恢复不重新初始化 |
| conversation/message | owner、lesson_session_id、role、content、sequence、status | 保存显示记录；失败/部分内容不等于完成 |
| agent_run | local request_id、operation、owner、lesson_id、base_revision、status、config_hash、bundle_hash、remote_id | 状态可追溯；unknown上游结果不自动重试 |
| remote_binding | local_conversation、platform_workspace、bot、remote_conversation、config_hash、epoch | 只能服务端写；不收客户端指定remote_id |
| action_candidate | run_id、kind、payload、status、base_revision、evidence_refs | 校验/确认后投影；不是正式测验事实 |
| quiz_session/question_snapshot | owner、lesson_id、difficulty、source_kind、review_status、revision、prompt/options/answer | 创建时快照；答案仅服务端 |
| quiz_attempt/hint_event | owner、question、answer、attempt、is_correct、request_key | 幂等；最终态不可重复计分 |
| learning_event | owner、event_kind、subject、source_request_id、idempotency_key、server_time、payload | 可信来源分级；append-only |
| learning_observation/memory_candidate | owner、status、evidence_ids、rule_version、override | 学生可质疑；不凭模型造事实 |
| recommendation_snapshot | owner、source_revision、items、reason/evidence | 事件触发更新；GET只读 |
| code_task_revision | 课程/知识点、starter、接口、可信测试规格、rubric | 参考解和测试不下发学生 |
| code_run/code_review | owner、task_revision、code_hash、result、deterministic_status、feedback_status | 错误分层，缺AI不覆盖测试 |
| job/worker_lease | task_type、payload、attempt、deadline、lease_owner、heartbeat | 原子领取；超时/孤儿重排受幂等保护 |
| audit/review_record | actor、对象版本、动作、时间、reason | 不存不必要的聊天原文和密钥 |

不要机械照抄“35张表”；此处是实体职责，不规定最终表数。可合并简单元数据，但不能合并不信任的草稿和已发布的权威事实。

## 4. 身份和租户边界

浏览器只持有自有应用会话，推荐同源HttpOnly会话cookie；所有写请求有Origin/CSRF检查，生产Secure，开发例外显式限定localhost。角色由数据库确认；管理员路由必须服务端拒绝学生，前端隐藏按钮不能代替权限。

本地学生ID、Knodo调用账号、Bot ID、Knodo conversation ID是四个概念。PAT代表其创建者，不代表消息里写的student_id。[P5,P8] 所有remote绑定按本地认证学生查找，客户端不能改变workspace/bot/remote_conversation。

**服务账号+不同conversationId不足以证明运行时隔离**：还要审查历史读取工具、共享文件、自动记忆、注入的认证变量和执行能力。公开资料不能证明这些对你的租户全部安全关闭。正式学生上线必须有平台提供的有效隔离方案或经验证的受限工具配置；无法收窄时阻塞真实学生使用，不能用提示词承诺补洞。双合成学生测试是回归测试，不是隔离形式证明。

不把学生创建为组织成员来绕开公开年龄条款。真实学生身份映射/M2M需要单独核对官方契约，不在MVP假造OAuth流程。

## 5. 教学上下文单一来源

本地从认证身份、课程发布版本、最新证据与策略生成snapshot。请求只含完成本次任务需要的数据：stage、grade（可空）、目标、少量当前课文、当前phase、已发生的结果摘要、允许引用/动作。不要发送手机号、学校班级、密码、原始日志、整份学生档案、其他学生数据或隐藏测试。

student_input/selected_text、导入资料、代码都标记为待处理数据而不是系统指令；这只是辅助约束，仍须依靠权限、输出校验和操作白名单。前端chapterId由后端反查权限/版本，不能信任前端提供的课文和学段。

初版不做本地向量库。短章节可直接提供有上限的发布内容；较长内容按知识点/小节确定性选择，额外背景由Knodo知识能力提供，但必须核实对应bundle版本与引用。预算限制用`*_chars/*_bytes`准确命名，不冒充token。绝不把JSON截断成半个对象。

Knodo工作区不默认挂整仓或全部25本跨学段资料。先使用限定的章节包和只含教学规范的空间；后续按能力验证分学段发布。若API无法选定所需知识范围，可用共享同一模板的分学段Bot部署实例或只使用本轮显式内容，记录限制；不能宣称平台已完成强学段检索过滤。

课程知识单向发布：源/审校 → 本地release → 导出manifest/hash → 平台部署 → 读取核对 → 绑定release。平台侧变更必须回收为草稿审核，不能在平台和本地各改一份正式教材。

## 6. 一次运行的事务边界

1. 验证本地session所有权、活动状态、输入大小、预算；处理request_id幂等。
2. 短事务：取得lesson/conversation的轮次租约，保存user message和agent_run，提交。网络请求不放在数据库长事务里。
3. 构建最小快照，调用平台目标Bot。request_id贯穿本地日志、可传递的平台字段（仅已证实时）和响应记录。
4. 把平台响应归一为业务结果，验证JSON schema、版本、引用、动作允许范围、文本安全策略。
5. 短事务：锁定lesson检查base_revision仍有效；写教师消息、候选、run终态和必要事件；不得从生成文本直接写考试成绩或完成状态。
6. 触发投影/后续动作；动作执行独立幂等。存在外部动作时不宣称跨系统恰好一次。
7. 释放/续租和finally清理；失联任务由租约回收，不按进程内布尔值推断所有权。

相同request_id+相同body：已完成重放；运行中返回run状态；相同key不同body返回409；已失败允许用户明确重试为新请求。超时且不知上游是否已接受记`UPSTREAM_UNKNOWN`，不盲重发。

## 7. 运行状态与流式

本地run状态：`QUEUED/RUNNING/SUCCEEDED/FAILED/CANCEL_REQUESTED/CANCELLED/STALE/UPSTREAM_UNKNOWN`。`CANCELLED`仅说明本地不再交付；另用`upstream_cancel_confirmed`表示平台确认。没有取消API证据时不能写远端已终止或不计费。

第一版使用**完整结构化返回、校验后展示**，通过自己的SSE推送run进度和最终卡片。这样更适合带动作的教学协议；等待时真实显示正在生成，不按16字符人为切片伪装上游流。平台具备安全可分离text流时再实施O04。

SSE建议事件：`run.started/run.progress/message.ready/action.ready/run.done/run.error`；每个有`run_id/request_id/sequence`，业务写成功后才发最终ready/done。heartbeat是注释或专门事件，不当首字；不把内部JSON、调试轨迹、工具参数、推理内容推给学生。

## 8. 代码执行边界

API不直接挂Docker socket。runner只接已授权的任务ID、受限代码和本地run凭据，不接任意image、volume、shell命令。runner不持Knodo PAT/主应用会话密钥；学生容器无网络、非root、readonly、cap-drop、no-new-privileges、CPU/内存/PID/超时限制。

stdout/stderr在读取过程中限流限量；大输出不能在内存全收完后截断。单次结果、图片数量/尺寸/总字节上限；产物经MIME/路径/大小验证后复制到应用存储。

清理只针对本Compose项目label+run_id+已到期租约，不能杀其他项目或仍活跃任务；禁止`docker system prune`。镜像构建进入新仓库，不依赖旧机器上的latest。

可信判分不能接受学生stdout里的“passed=100”。优先让可信测试驱动保留预期答案，把学生函数通过JSON输入/输出在容器内执行，由外侧比较；初版只支持迁移的受控函数任务。若复用pytest夹具，逐条核实执行/结果通道与隐藏资料边界：只读挂载不等于不可读取，不得声称绝对防作弊。隐藏测试与参考解不发前端、不发Tutor、不出现在运行回显中。复杂防作弊系统不是本赛题MVP目标，但不能有明显自报成绩通道。

保留[K3]的评分边界和系统错误不扣学生分原则；AI无效/超时只影响AI评价，真实测试结果仍显示。若输出总分需要AI分数，缺失时不拿0分悄悄补齐，显示“AI评价未完成”。

## 9. 存储、后台与启动

新Compose项目名建议`shuangling-knodo`；开发API建议18082、Web15174、PG15432，作为可覆盖默认值先查占用，不杀既有进程。测试使用不同project/db/ports（如k12_knodo_test），数据库名称检查+显式TEST_DATABASE_URL，任何重置要求确认是测试资源。

一条bootstrap：依赖检查 → migration → 来源/结构校验 → 幂等导入发布课程/资源/审校题/代码任务 → 可选合成demo账户 → 启动API/worker/Web → doctor核对服务身份、版本与内容数量。不能把登录成功当所有内容初始化成功。正式可用性检查不能偷偷调用付费模型。

liveness只检查进程；readiness检查DB/迁移/存储/必要worker，AI依赖另列capability状态；CodeLab检查runner与镜像，未启用就不谎报健康。后台任务失败可在管理界面检查，不一直转圈。
