# 霜铃 K12 × Knodo：从零重建总计划

版本：2.0｜核查日：2026-09-18｜目标目录：`/home/zxk/Projects/K12`

## 0. 这次决定与上一轮有什么不同

这是一个**新建独立应用、以 Knodo 为教学 Agent 运行平台**的计划，不是给旧系统增加一个可选聊天 Provider。用户已经选择从零重建，因此不再执行上一轮“先修旧系统 M0，再接一条聊天分支”的范围。旧项目只读保存，内容、纯业务算法、测试思想和可用视觉资产按清单迁移，不整仓复制，不先清空旧目录。

“从零”指新应用结构、新数据模型和初始化、新接口与前端教学流程；不意味着丢掉已积累的课程和正确性约束。也不意味着所有代码都放进 Knodo：平台负责通用 Agent 运行与教学生成，自己的应用负责学生体验、可靠业务事实和受控执行。

本文中的新目录、角色、操作类型、接口、状态、数量目标、验收门槛均为**本项目设计**，不是 Knodo 官方定义或赛事原文。官方事实以 [F1]/[P*] 为据，仓库事实以 [K*]/[C*] 为据。完整出处见 `references/source-index.json` 与 `plans/08_证据与限制.md`。

### 1.4 CareerMate应该借鉴什么

它不是“网页直连平台后全部完成”。客户端通过服务端调用百宝箱，本地仍保存权威业务数据；V2组织任务上下文和证据快照，解析候选，确认后再做业务投影。[C1,C2,C3,C4,C7]

应迁移的**模式**：平台资产入仓；任务/证据/业务结果分层；远端会话绑定；候选与事实分离；校验与确认；真实/Mock分开验收。可借鉴流信封过滤测试，但过滤不等于内容安全。[C5]

不迁移：百宝箱的Authorization格式、`question/business_data/agent_version`等wire字段；职业/简历/岗位业务；SQLite迁移；危险的开发seed清库流程；为了保留历史而堆叠多套legacy路径。MCP不是CareerMate主聊天必经步骤，不必为了“平台化”先做MCP。[C1,C2,C3]

## 2. 赛题应该怎样完成

### 2.1 硬性要求和评分项分开

[F1]要求按四学段或教材匹配知识、风格、难度，既能提问也能主动章节引导；六类交互至少三类；记录历史，依据答题和兴趣调整推荐；交付可运行原型、集成部署方案与报告。

评分权重：智能体设计25%，多模态25%，教育适配20%，体验15%，创新15%。没有公开更细评分细则，不给预估得分。

**不是必须项**：六类全做、多Agent数量、知识图谱、向量数据库、排行榜、家长端、iframe、Kubernetes、断点调试器。这些不能因出现在旧审查缺口里就变成开发任务。

### 2.2 新项目的产品定位

> 霜铃是一位围绕人工智能通识课程组织学习的AI伴学教师：根据学段和当前学习证据，带学生完成“理解目标—讲解—操作/实践—检查—反馈—下一步”，并让学习建议有出处、学习记录可追溯。

主界面是**一节课的学习工作台**，不是把书库、聊天、编程和画像堆成互不关联的菜单。阅读器和教学对话共享章节版本；练习、资源和代码任务通过受控卡片在同一学习上下文中打开。

### 2.3 发布范围：先做五类，绘本明确后置

| 类别 | R1必须交付的可演示能力 | 不可冒充的替代品 |
|---|---|---|
| ①问答 | 真实Knodo教师，当前章节依据，四学段表达差异，追问与复盘 | Mock回复、仅换模型网关 |
| ②教学资源 | 至少真实Word/PPT文件和一个教学视频资源；可预览、播放或下载，有来源与章节关联 | 只有RAG命中/文件名/失效URL |
| ③动画讲解 | 至少两个可暂停、单步、重置的概念动画；与练习使用同一算法事实 | 桌宠帧动画、加载动效 |
| ⑤在线编程 | 初学者代码框架、真实隔离运行、报错定位、确定性结果、AI解释 | 模型假装执行、宿主执行学生代码 |
| ⑥趣味练习 | 自动组织/生成章节小测，至少一种步骤排序或匹配题，真实判分与分层反馈 | 只加徽章或漂亮卡片 |
| ④绘本（增强O01） | 有图、有分页互动、有课程目标；生成稿审校后可用 | 只有分镜文本、装饰占位图 |

上述五类及最低产物数量是本项目目标，不是赛题强制数量。Word/PPT可用经审核的现有或团队制作文件，不要求Knodo原生生成二进制；视频可用自录教学动画导出或有授权的资料，必须实际存在。语音作为低龄体验增强，不把语音输入/播报单独拆成第七类。

### 2.4 四学段样板

建议划分1–3/4–6/7–9/10–12年级，具体分界是项目规则。[F1只给学段名称]
R1每档至少一节经过审校的示范课；其中先深做小学高年级、初中各一节，再补低龄与高中。示例主题是设计建议而非旧教材已存在章节：低龄“电脑怎样认出不同物品”，小高“把步骤排对”，初中“查找与条件循环”，高中“训练数据与简单分类”。

旧书`ai-primary-fun`从三年级开始，不能直接标记适合一、二年级。高中选题应保留AI通识目标，避免系统变成纯Python刷题站。每节课给出目标、先备知识、活动、练习、可用资源、任务、评估证据和不适用范围。

## 3. 技术栈与部署取舍

| 层 | 决定 | 取舍理由 |
|---|---|---|
| Web | React + TypeScript + Vite + React Router + TanStack Query；Tailwind；CodeMirror | 复用K12前端经验与编辑器，不因CareerMate用Next.js而改栈 |
| API | Python 3.12 + FastAPI + Pydantic + SQLAlchemy async + Alembic + httpx | 保留Python课程/评分/沙箱迁移便利；后端只做业务与平台集成 |
| 数据 | 独立PostgreSQL；正常关系表+受约束JSON | 新库不接旧库；不默认装pgvector、不搬旧embedding |
| 后台 | PostgreSQL任务表+独立worker | 平台调用、内容处理、投影任务有状态；不引入Kafka/Celery |
| 状态与限流 | PostgreSQL权威轮次租约；单实例本地限流，公开多实例时外部限流/Redis | 不把进程内锁当全局锁；默认不用Redis增加运维 |
| 文件 | local存储接口起步，S3后续适配；同一volume与根配置 | 不重复建MinIO装饰服务；多实例部署前再验证共享存储 |
| Agent | Knodo Tutor/Designer Bot，系统提示词+Skill源码入仓 | 不新增本地planner/tool-loop/双重自动记忆 |
| 代码执行 | 独立runner边界，Docker一次性容器，构建文件入仓 | API无Docker socket，执行器不持有Knodo/学生会话密钥 |
| 测试 | pytest、前端组件测试、Playwright、契约fixtures、真实平台验收脚本 | 环境、Mock、真实调用、人工审查分列 |
| 演示部署 | Compose + Web反向代理 + API + worker + PostgreSQL；runner独立受控 | 不把Knodo站点发布当成自有K12全栈托管保证 |

具体依赖版本在T04核对兼容性后一次锁定；沿用Python3.12和React19的已知项目基线可作为起点，但不把历史补丁版本写成当前最新。提交锁文件，后续任务禁止顺手升级。Node/pnpm以执行机实际安装和Vite兼容要求记录，不硬编一个未来版本。

## 4. 平台与本地的分工

```text
学生浏览器
  学习工作台 / 书库 / 练习 / CodeLab / 成长
                    ↓ 自有会话认证
FastAPI：身份与权限 → 课程/学生最小上下文 → 教学会话/幂等
  ├─ KnodoGateway → Tutor Bot → 教学文本、引用、下一步建议
  ├─ KnodoGateway → Designer Bot → 题目/资源规格草稿
  ├─ 校验器 + 候选策略 → 测验/资源/任务服务
  ├─ 学习事件 → 证据投影 → 下一步内容
  └─ 代码任务 → runner → 隔离学生容器 → 可信评分
PostgreSQL：本地权威事实；文件存储：已审核发布的资源
```

**两类Bot，不等于依赖平台自动子代理编排。** 两类调用由本地确定性的操作路由发起，不做本地自主Agent循环。Tutor负责`TEACH_TURN/CODE_FEEDBACK`；Designer负责`QUIZ_DRAFT/LESSON_PACKAGE_DRAFT`。一个完整学习回合可以按状态先后使用两者，但不每条消息机械串两次模型。

Tutor看不到Designer的答案库或隐藏测试，也不把生成题目的远端会话复用为学生自由聊天。Designer默认只接收课程/题型/学段规格，不接真实学生身份或整段聊天；所有生成稿与已审核题库分开。

课程版本、本地学生事实、AI建议各有一个主人：课程以发布快照为准，学生事实由本地事件与业务事务生成，Knodo输出是建议或草稿。不能因为模型说“测验完成了”就写完成记录。

## 5. 如何让Knodo成为真正底座而不是挂名

真实教师、动态教学反馈、AI题目/资源草稿都通过Knodo目标Bot执行，配置与Skill可由平台团队独立更新；源码保存配置hash、课程bundle版本和验收样例。新项目不保留隐藏的直连LLM主链路，不在平台失败时静默切回旧Provider。

允许 `knodo` 与 `fixture` 两种运行模式。fixture只为离线开发/测试，必须全局可见标识，正式演示启动检查拒绝fixture。平台不可用时，已发布课程/已创建测验/确定性代码运行仍可用；AI入口如实显示不可用，不假装有真人教师回复。

本地保留的状态机、权限、判分和候选校验不是重新自研一套Agent，它们是教育业务规则。MCP可后置：第一版用一次请求内的最小上下文与受校验结果，不给平台通用数据库读写工具。[C2,C6,P3]

## 8. 验收不是“页面能打开”

至少要证明：四档有真实差异；进入章节自动引导但刷新不重复；题目与当前版本匹配；服务端判分；结果改变下一步；资源可打开；动画步骤正确；代码实际隔离运行；记忆可质疑/遗忘；换学生不串数据；真实Knodo日志与本地request_id可关联。

发布目标不是“全测一片绿”这个数字，而是相同新库、正式启动路径、真实所需依赖下核心脚本可复现。Mock用例不能冒充真实教学质量，历史通过数量不能沿用。

真实评测建议复用旧37条作为候选素材，先审查是否仍适配新需求，再加学段、主动教学、隔离、生成资源和异常场景。记录样本、配置、失败、用量、可见回复时间和人工判断；阈值是团队拟定门槛，不是赛事标准。没有价格/积分换算依据时不算人民币成本。

## 9. 必须人工承担的少数事项

团队确认平台租户、凭据与调用预算；获取登录后的API契约；核对两类Bot实际配置和权限；内容审核者签审教材/素材/题目；真实学生试用前确认适用安排。代码Agent可以生成清单、材料包和自动测试，不能代签人工审校或伪造授权。

## 10. 交给执行Agent的方法
