> 本书由霜铃 K12 教学助手独立编写，面向第一次借助 AI 编程工具完成项目的学习者。这里把 Vibe Coding 当作一种协作实践来讲，不把它当成有唯一标准的语言或工具。重点是如何表达需求、检查代码、处理风险并完成作品；示例可用于 Codex 或其他编码助手。

## 第1章 Vibe Coding 是协作方式，不是免学编程

Vibe Coding 常用来描述：开发者用自然语言表达目标，编码助手帮助阅读代码、提出方案、改动文件、运行命令并修复问题。它缩短了一些重复劳动，但没有消除软件工程。你仍需要决定做什么、什么结果算完成、数据应如何保护，以及生成的代码是否正确。

把它想成带工具的结对编程：你负责目标、约束、优先级和最终判断；助手负责基于当前上下文提出并执行候选改动。助手说“完成”只是一个待验证的陈述。只有跑过的程序、实际页面、命令输出和审查过的差异，才能证明结果。

新人常见的两种误区是把大项目一次性丢给 AI，以及因为页面看起来能动就认为功能完成。更稳的做法是缩小任务：先做一个用户可见的完整切片，再用真实输入验证；需要时不断修正方向。

这种协作尤其适合重复代码改动、已有项目的小功能、测试草稿和验收清晰的界面。它不适合把法律、医疗、安全或未成年人决策直接交给模型；这类任务需要专业责任人和独立审核。工具越能操作真实系统，越要限制权限并记录行为。

把“快”拆成可观察过程：助手可能让第一版更快出现，但整项工作仍包含需求确认、项目理解、代码审查、验证和交付。若需求反复变化、上下文不足或接口不清，AI 可能更快地生成错误方向的代码。先花几分钟澄清目标，通常比之后大面积返工更省时间。

**练习**：用一句话描述一个你想做的小工具，再写出“什么现象能证明它真的有用”。不要先写技术栈。

## 第2章 从想法写成清楚的任务说明

含糊的想法通常缺少使用者、情境和可验证结果。把“做个课程平台”缩小为“学生能搜索三门本地课程，并打开其中一门查看章节”。后者可以明确检查，不会鼓励助手自行发明登录、支付、推荐、社交等旁支功能。

写任务时回答六个问题：

1. 谁在什么情境下遇到什么问题？
2. 这次要交付的最小结果是什么？
3. 用户从哪里进入、经过什么操作、看到什么结果？
4. 哪些条件不能改变，例如已有登录、接口或版式？
5. 哪些内容明确不在本次范围？
6. 用哪些可观察步骤判断完成？

例如：“为课程卡片增加按标题筛选。搜索框放在现有课程列表上方；输入后列表即时更新；清空后恢复全部课程；没有结果时显示明确空状态。保留现有 API 和收藏行为。本次不增加后端搜索、不改课程数据结构。验收：搜索已有课程名、搜索不存在的词、清空搜索，并确认收藏按钮仍可用。”

每句话都应该减少歧义。若你发现需求中出现“高级”“漂亮”“智能”等词，就补一个具体例子或验收标准。

可以把说明写成小型规格：

```text
用户：初中学生
场景：在学习书库里查找 Python 教材
输入：书名或章节关键词
输出：匹配的本地教材卡片；没有匹配时显示空状态
限制：不离开当前应用；不改变现有登录和课程接口
验收：搜索“循环”能找到 Python 教材；搜索随机字符串显示无结果；清空后恢复三本书
```

规格里写“发生什么”，不要抢先规定所有内部实现。告诉助手必须保留哪些接口和行为，其他细节可以让它检查后提出最小方案。若项目有必须遵循的技术栈或设计系统，明确写出来。把需求写到同学能用相同步骤验收，比写一串形容词更有用。

**练习**：把“帮我做一个好看的记账页面”改写成包含对象、流程、输入、输出、边界和验收步骤的一段任务说明。

## 第3章 写出助手容易执行的提示词

一条有效任务提示通常包含：目标、项目上下文、允许改动、限制、验收。不要只说“帮我做得更好”，要告诉助手看哪些页面、保留哪些行为、交付什么状态。

一个可复用的结构：

```text
目标：给课程目录增加标题搜索。
上下文：用户从 /resources 进入，列表由现有学习目录接口提供。
行为：输入关键词后筛选标题；清空后恢复全部内容。
约束：保留收藏按钮和移动端布局，不新增依赖，不改变后端协议。
验收：用一个存在的关键词、一个不存在的关键词、清空搜索各检查一次。
请先查看相关组件和已有测试，再做最小改动，并报告实际验证结果。
```

提示词越长不一定越好。只给当前任务需要的背景，避免无关的代码规范、旧会议记录和长篇说明把重点淹没。把稳定规则放在项目说明文件里，把本次目标放在任务提示里。对代码修改，使用项目名词和真实路由；对不确定之处，说明助手可以做出的低风险假设。

如果需要逐步协作，要求它先总结当前行为与拟改位置，再实施；如果任务范围很清晰，也可以直接让它完成并验证。提示词应引导工作，而不是替代审查。

逐步任务要给每个阶段一个结果和停靠点：先只读检查并反馈相关文件；再改一个核心流程；随后运行指定检查；最后总结改动与未验证风险。提示词里可以加入具体边界：“不要新建数据库表，因为本次只做静态教材页面”比“不要做太多”清楚。

如果助手发现接口与描述不符，应让它指出证据并调整方案，而不是要求它继续按旧假设编码。验收标准要写成可执行步骤；“效果不错”“交互流畅”不容易复现，最好说明用户操作后页面应出现什么。

**练习**：用上面的结构为“记账页面增加月份筛选”写一份提示词，加入至少两条不能破坏的已有行为。

## 第4章 让助手理解项目，而不是猜项目

开始修改前，先确认当前目录、应用入口、相关组件和数据来源。通过搜索页面标题、路由、接口调用和样式名找到实际实现。不要假设文件名、框架版本或数据库状态；用户代码可能有尚未提交的改动。

给编码助手的项目上下文应短而有用：技术栈和版本、运行方式、测试命令、数据边界、不能触碰的服务，以及重要架构约定。规则适合写在项目说明文件，详细的专题解释可以放在对应文档。不要要求每个微小改动都读完所有文档。

检查前端和后端的真实契约。一个按钮可能调用多个 API，一个列表可能按用户年级过滤。只改前端显示、不验证接口语义，容易做出“看上去正确、实际数据错位”的功能。遇到复杂操作，先追踪一条从界面到服务端再回来的数据链。

一个可靠的上下文总结包括：相关文件、当前行为、依赖版本、已知限制、如何复现。把“当前行为”与“希望行为”分开，避免模型把旧实现误认为需求。

给上下文时区分事实与假设。事实写“搜索由 `listCatalog` 请求服务端目录”；假设写“我猜书名搜索应覆盖章节标题”。让助手先检查假设，并在发现相反证据时据实说明。不要把整份数据库备份或无关用户档案交给模型；只提供完成当前任务所需的脱敏样例。

上下文文件也需要维护。任务结束后，更新已经过时的启动命令或接口说明；不要每次失败都往项目说明里追加一条特殊规则。长期有效、跨任务复用的约定放在项目文档，某次临时上下文放在任务描述中。

**练习**：从一个已有项目中选一个按钮，写出它的 UI 文件、调用的 API、服务端处理位置和一个验证办法。

## 第5章 把大作品拆成可运行的小步

大需求应拆成垂直切片，而不只是先写完所有模型、再写完所有页面。垂直切片从界面穿过接口或数据层，最终完成一个最小用户流程。例如先支持一条课程的展示与打开，再扩展搜索和收藏。

每个小步都要有一个完成条件：文件存在、按钮可点、数据正确、错误可见。步骤之间要有稳定接口，不要同时改一堆互相依赖的模块。优先做风险最大的部分，例如权限、文件上传或状态同步，因为越晚验证越难定位问题。

为了控制范围，可把任务标成三类：必须有的基础流程、提升体验的增强项、暂不做的旁支。先确保一条主要流程真实可用，再增加动画、复杂推荐或管理面板。

一次迭代可以这样结束：记录已完成的行为、失败的检查、剩余风险；下一轮根据证据决定继续、修复或调整设计。任务拆解的价值不是写一份漂亮计划，而是让每一步都可以运行、检查和回退。

一个“课程收藏”切片可按如下顺序完成：先显示收藏按钮和真实状态；再接入添加/取消收藏接口；然后覆盖未登录、重复点击和网络失败；最后检查回到页面后状态是否一致。每一小步都触达真实用户路径，避免只完成孤立后端字段或没有数据的漂亮卡片。

切片要小到一两轮能理解和验证，又要大到足以让用户看到有意义的变化。如果一次改动只添加没人使用的抽象层，它不是用户价值切片；如果一轮同时改十几个流程，出错时又很难定位责任边界。

**练习**：把“做一个在线测验平台”拆成五个顺序任务，第一步必须能由一个学生独立操作并看到结果。

## 第6章 与编码助手一起实施

进入实施时，把任务限制在一个用户流程或一组紧密关联的改动内。先让助手指出相关代码，再提出最小修改；如果方案涉及新依赖、数据库迁移、认证或数据删除，先单独说明影响，必要时让人决定后续动作。

写代码时继续提供反馈证据，而不是只给感受。“手机上卡片超出屏幕 24 像素”比“手机看起来不对”更有效。“第二次点击会产生两条相同记录，浏览器网络面板显示两个 POST”比“按钮有 bug”更便于修复。

接口边界要清晰。前端传来的 ID、数量、文件名和角色都要重新验证。不要因为助手能调用 shell 或数据库就把真实凭证直接给它。外部服务依赖要列明用途和版本，并遵循项目已有的配置方式。

实施之后检查差异：删除了什么？新文件里是否包含密钥？是否改动了本次目标以外的导航、接口或样式？助手应提供改动清单和实际运行的命令；没运行的检查应明确标为未验证。

较好的实施提示会要求：先读相关代码；只改本次功能所需文件；遵循当前组件和接口风格；处理加载、空、错误和成功状态；实施后指出每个改动对应哪个验收条件。不要要求“把代码重构得更现代”，除非重构本身就是目标。

如果方案新增依赖、数据库迁移、认证或数据删除，先单独检查其影响。低风险本地修改可以继续；扩大系统边界的变化应该先向项目负责人说明用途和代价。模型能调用命令不等于命令就是安全的。

**练习**：请助手增加一个小型表单，然后逐项检查新增字段是否校验、提交是否去重、失败是否给出用户可理解的反馈。

## 第7章 验证代码，而不是信任生成结果

AI 可以生成语法看起来合理、但边界条件错误的代码。验证流程从最低成本开始：静态检查、类型检查、单元测试、接口集成、浏览器交互、部署前检查。具体顺序根据项目决定；重要的是验证真实行为，而不只是看 diff。

为每项验收标准配一个证据。例如“清空筛选恢复结果”要实际点击清空并观察列表；“权限隔离有效”要用两个不同账号请求同一对象；“移动端适配”要检查实际窄视口的横向溢出。

测试数据要接近真实边界：空数组、缺失字段、极长文本、错误编码、并发双击、刷新和断网。测试通过只说明覆盖到的情形通过，不代表所有组合都正确。

如果一次改动连基础构建都没跑过，不应宣称已经可交付。检查失败时先读首个相关错误，确认错误是否由本次改动引起，再修复最小原因。不要为了让检查“变绿”而删除有价值的断言。

维护一张简短验证记录：检查名称、执行命令或操作、通过/失败、失败原因。UI 验收要记视口和关键操作；接口验收要记请求状态和返回内容。截图能显示外观，却不能单独证明收藏已保存在服务端；类型检查通过也不能证明手机页面没有横向滚动。

区分代码验证和产品验证。构建、类型检查和单元测试提供代码证据；学生是否能完成任务、错误提示是否可理解、键盘能否操作，则是产品证据。两类都重要，但回答的问题不同。

**练习**：为书库搜索功能写四条手动验收：正常命中、无结果、清空恢复、极长关键词；记录每条实际观察到的结果。

## 第8章 调试：从复现到根因

调试从稳定复现开始。写下操作步骤、预期结果、实际结果、环境与错误信息。一次只改变一个变量；如果问题只在手机出现，记录屏幕尺寸和浏览器；如果只在某账号出现，先检查权限和数据状态。

可以按边界逐层排查：输入是否正确进入组件？请求参数是否正确？服务端是否收到？数据库结果是否符合过滤规则？响应是否被前端正确解释？界面是否被旧状态覆盖？在每个边界记录最少必要数据，避免输出密钥或学生隐私。

给编码助手的调试提示应包含真实错误与尝试过的操作，并要求先提出能区分不同根因的检查。比如“首次打开章节正常，刷新后 404；路由配置包含 `/chapters/:id`，nginx 静态回退未确认”。这比直接要求“重写路由”更能保留现有架构。

修复后用原复现路径验证，再检查一个邻近流程。只有确认结果来自新代码，而不是缓存、fixture 或旧服务，才能认为问题已修复。

不要一次要求助手“尝试所有可能修复”。先列出两三个假设和区分它们的检查。例如搜索结果为空，原因可能是请求没发出、后端按错误学段过滤、前端搜索词未提交或卡片过滤错误；查看网络请求、响应和 DOM 结果就能依次排除。

修复总结应说明根因、造成的行为、修正方式和复现路径。只调高超时、吞掉异常或隐藏错误页可能掩盖问题；确认新代码真正消除了根因，而不是让症状暂时消失。

**练习**：模拟一个“列表显示旧数据”的问题，分别检查缓存、请求参数、后端过滤和 React 状态更新，写出每层的一条证据。

## 第9章 界面作品：先让使用者看懂

界面设计先回答三个问题：用户来到这里要完成什么？下一步在哪里？当前状态是否清楚？标题、说明、主按钮和结果区域应按重要程度排列。颜色和阴影不能代替信息层级。

从窄屏开始定义布局，避免固定宽度让内容溢出。检查正文换行、长标题、可点击区域、焦点顺序、表单错误和空状态。颜色不是唯一提示；图标旁边仍应有文字。键盘用户应能完成主要操作。

让 AI 做 UI 时，提供文字风格、布局结构、现有设计变量、目标视口和参考截图。生成后在浏览器看真实页面，关注滚动、折叠、导航和错误状态。静态截图不一定覆盖异步加载后的页面。

一次视觉改进最好对应一个目标，例如让搜索更容易找到，而不是同时更换字体、配色、卡片圆角、动效和导航。改动太多会让你难以判断哪一项解决了问题。

可以依照四层顺序检查界面：信息层级（标题、说明和主要动作是否一眼可见）；状态反馈（加载、无结果、失败和成功是否都存在）；交互可达性（Tab、Enter、焦点和标签是否合理）；响应布局（320px、768px、桌面宽度是否出现覆盖或横向滚动）。不要靠缩小字体掩盖溢出；应允许内容换行或调整布局。

截图评审要比较同一个目标：先记录“移动端搜索框和教材标题会互相挤压”，再调整布局，并用同一视口复查。使用稳定的颜色、间距和字体层级让多个页面看起来属于同一产品，而不是每页重新发明一套样式。

**练习**：画出学习书库在 375px 和 1280px 两种视口的草图，标出标题、搜索、筛选、教材卡片和无结果状态。

## 第10章 数据、安全与自动生成代码

编码助手可能生成能跑但不安全的代码。所有来自用户、浏览器、文件或模型的输入都是不可信的：服务端重新校验、查询绑定参数、文件限制类型和大小、输出按上下文编码。隐藏按钮不等于权限检查，前端角色值不等于身份凭据。

密钥使用环境变量或专门密钥存储；永远不要提交 `.env`、访问令牌或真实用户数据。只为当前任务开放最少的数据库、网络和文件权限。运行模型生成的 shell 命令前看清它会改动什么；不确定时先用只读命令或隔离环境。

新增依赖要解释来源、功能、许可证和维护状态。文件操作应限制在指定目录；避免根据模型输出直接拼接 shell 命令、SQL 或路径。涉及发送邮件、删除记录、支付、公开分享等副作用时，应显示预览并获取用户确认。

安全审查要沿数据路径走一遍：谁能发起请求？服务端如何确认身份？对象归属在哪里检查？模型生成的参数如何验证？工具失败时会不会泄漏内部路径、数据库错误或令牌？日志是否只包含排错所需的信息？前端隐藏入口不能替代后端授权检查。

对任意文件路径，拒绝绝对路径和 `..` 路径穿越；对外部网址设允许范围；对 SQL 使用参数化查询；文件上传限制大小和类型。编码助手生成的测试账号、密码和 API key 也不能提交到真实配置或截图中。

**练习**：审查一段“按用户输入路径读取文件”的代码，列出路径遍历、权限越界、超大文件和错误信息泄漏的风险，并设计验证点。

## 第11章 Git：让尝试可以比较和撤回

Git 保存项目历史，使你能查看助手改了什么、比较前后版本并在需要时回退。开始任务前先查看工作区状态，辨认哪些改动是自己已有的，避免把其他工作误认为助手产物。

一个常见的安全节奏是：建立独立分支或备份点；完成一小段可运行改动；看 `git diff`；运行相关验证；确认后再提交。提交信息描述用户能理解的变化，例如“增加本地 Python 教材阅读页”，不要写“updates”。

`git status` 看工作区，`git diff` 看未暂存差异，`git diff --staged` 看已暂存差异，`git log --oneline` 看近期历史。`git restore`、`reset`、强制推送可能丢失工作；使用前必须确认目标文件和范围，不要用这些命令盲目清理。

分支合并冲突说明不同改动触及相同区域，不是“Git 坏了”。逐段理解两边改动后再合并；不能确认时保留两边并询问作者。

常见安全操作：

```bash
git status --short
git diff -- path/to/file
git add path/to/file
git commit -m "添加本地教材阅读页"
git log --oneline -5
```

每次暂存前看状态与差异，尤其不要用 `git add .` 把无关文件、生成物或本机配置一起提交。一个小而完整的提交便于比较；提交前再运行受影响的检查。查看历史能帮助定位“什么时候出现差异”，但不要用改写历史的命令清除他人协作痕迹。

**练习**：创建一个小分支，改动一句说明，查看 diff，再撤销这项改动。记录每条命令影响的是工作区、暂存区还是历史。

## 第12章 交付、演示与维护

能启动的程序不一定能交付。让第一次打开项目的人知道前置条件、安装、启动、登录、主要流程、测试方式和已知限制。不要把本机绝对路径、密钥或个人账号写进文档。

演示流程应从用户目标开始，例如“找到 Python 教材、打开函数章节、跳转至练习”。准备确定的测试账号和本地数据；明确哪些结果来自真实后端，哪些是演示夹具。网络不稳定时准备离线替代，但不要把模拟结果说成真实服务返回。

交付前核对：构建成功、关键流程跑通、空与错误状态可读、窄屏不溢出、凭证不在提交中、依赖和启动步骤明确、修改范围清楚。记录尚未验证的浏览器、账号或数据边界。

好的演示不追求隐藏失败，而是让观众知道系统如何处理失败。一个诚实的“暂时无法加载，请重试”比无声空白更能说明作品的完成度。

交付说明让第一次打开项目的人无需口头补充也能启动：前置软件版本、安装命令、环境变量名称（不写值）、数据库初始化、启动方式、测试账号来源和演示路径。演示数据如果是合成的，应明确标注，避免把离线模拟说成真实服务返回。

发布前再检查依赖清单与静态构建目录，确认没有调试日志、硬编码本机路径、试验代码和外部服务密钥。对尚未支持的流程写明限制；清楚的限制比承诺“之后都能做”更可靠。

**练习**：为本项目录制一段两分钟演示脚本，包含成功流程、一次搜索无结果和一次刷新恢复，并标出每段需要准备的数据。

## 第13章 综合练习：从一句想法做成学习书架

目标：在现有 Web 项目里新增三本本地教材卡片；点开后在应用内阅读 Markdown；目录能跳转章节；搜索标题与主题；窄屏能使用；不显示旧的合成示例课程。

先写验收：默认能看到三本教材；书名和章节数准确；卡片点击进入本地路径；阅读页显示正文与目录；目录项跳到对应标题；搜索 `Agent` 能找到 Agent 教材；搜索不存在的词时显示空状态；移动端无横向溢出；示例夹具不出现在书库卡片。

把实现拆成三个切片：一，静态教材元数据和书库卡片；二，读取本地 Markdown 的章节阅读页；三，搜索、目录和窄屏交互。每个切片都先运行，再进入下一步。只改这项功能相关的导航和样式，不重写账户或课程后端。

完成后邀请另一名同学按验收清单操作。记录实际结果，不要只展示一张首页截图。若内容、交互或数据和预期不一致，回到最小复现再修。

给编码助手的起始任务可以是：“先检查项目的 `/resources` 页面、登录边界和现有内容卡片。不要改文件。列出三本本地教材需要的元数据、路由、页面文件和将要验证的用户流程；标出可能与示例课程冲突的地方。先给我检查方案，再开始实施。”确认方案后，再分别下发卡片、阅读器和搜索三个小任务。

最终演示按用户目标走：登录学生账号，打开学习书库，搜索“Agent”，进入教材，点目录跳到 Guardrails 章节，再返回书库搜索“Python”。这个流程同时验证本地正文、目录锚点、搜索和返回路径，而不需要把外部站点当作产品内容服务。
