## 第1章 从聊天回答到任务执行

聊天模型通常接收一段输入并产生一段输出。Agent 工作流把模型放进一个有边界的任务循环：理解目标、判断是否需要工具、提出工具调用、接收工具结果，再决定继续还是结束。若任务需要多个步骤，模型可能多轮推理并调用多项工具；程序必须负责把每一步连起来。

一个可用的 Agent 系统至少有五个部分：模型负责生成下一步；指令说明目标与行为边界；工具让系统读取数据或执行操作；运行器负责工具调用、继续循环和结束条件；应用保存状态、管理身份、验证权限并决定哪些动作需要人工确认。

“Agent 会自主行动”不等于“Agent 应拥有全部权限”。要先画清楚信任边界：什么数据可以传给模型、工具能访问哪些对象、能否改变外部状态、失败时如何停止。查询课程目录与删除账号的风险完全不同，权限应按用途分别设计。

把 Agent 说成“会自己做事”会掩盖工程细节。较准确的说法是：模型提出候选步骤，运行时按已配置能力执行并返回观察结果；每个工具的实际权限仍由应用代码决定。

可以用一个简单闭环理解：用户目标 → Agent 选择回答或工具 → 应用执行工具并检查权限 → 结果返回 Agent → Agent 总结或继续。模型负责判断下一步，不直接获得数据库权限。应用仍要对认证、业务规则、工具副作用、日志和恢复负责。

Agent 与固定规则工作流也不同。纯粹的步骤（例如“校验邮箱后保存表单”）用普通程序更容易预测；需要根据开放文本选择工具、综合多份证据或调整步骤时，才让模型参与决策。不要为了使用 Agent 而把简单 if/else 交给模型。

**练习**：为“帮学生找一节关于循环的课程”画一条流程，标出模型、课程查询工具、权限检查和最终回答各自负责什么。

## 第2章 选择运行方式：Responses、Agents API 与 SDK

OpenAI 的官方文档区分几个不同层级：Responses API 适合直接调用模型并由应用编排；Agents SDK 在自己的应用中运行，适合希望控制工具、状态与集成的团队；Agents API 则使用托管的 Agent 运行时，由服务管理会话和执行环境。它们不是同一个 API 的不同叫法，状态对象、工具执行位置和运维责任也不同。

选择前先回答三个问题：运行循环由谁控制？会话状态存在哪里？工具在哪个环境执行？如果只需要一次模型响应，先用更简单的调用方式；如果应用要持久会话、自定义工具、人工审批或多步流程，才考虑完整 Agent 运行时。

本书用 Agents SDK 举例，因为它适合清楚展示本地服务中的 Agent 结构。SDK 不会自动替应用保存所有业务数据、自动授权数据库访问，或替你完成部署。选择 SDK 意味着应用要承担工具权限、存储、审批和错误恢复等责任。

不要从“多 Agent 更高级”开始。单个 Agent 配一个窄职责和少量工具通常更容易调试。只有当不同分支确实需要不同权限、指令、输出责任或团队维护边界时，再把工作拆给多个 Agent。

可以用这个顺序选择：只要生成一段文本，先考虑普通模型调用；需要模型触发一个确定函数，考虑工具调用；需要多轮工具循环和多个专家时，再使用 Agent 编排；需要托管会话和执行环境时，才评估 Agents API。每增加一层运行时，就多承担一份追踪、恢复和安全工作。

本书不会假定平台账号一定具备某个 API、模型或沙箱权限。运行前确认项目已开通的模型与功能；不要把官方示例中的模型字符串当成所有账号永久可用的保证。

**练习**：分别为一次性问答、需要数据库查询的客服流程、可暂停并等待人工批准的退款流程选择运行方式，并写出你选择它的原因。

## 第3章 建立第一个可运行的 Agent

先准备 Python 环境，并把 API 密钥放在环境变量中。不要把真实密钥写进脚本、截图、课程文档或 Git 提交。

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install openai-agents
export OPENAI_API_KEY="你的平台密钥"
export OPENAI_MODEL="你的项目当前可用模型 ID"
```

Windows PowerShell 激活方式为 `.venv\Scripts\Activate.ps1`；环境变量可用 `$env:OPENAI_API_KEY="..."` 设置。项目可以把模型 ID 放在本机配置中，但不要把密钥和模型名混为一谈。

保存为 `first_agent.py`：

```python
import asyncio
import os

from agents import Agent, Runner

agent = Agent(
    name="学习计划助手",
    instructions=(
        "帮助学生把学习目标拆成小步骤。"
        "如果用户没有说明年级或时长，先问一个必要的澄清问题。"
        "不要声称已经安排了日历或完成了实际操作。"
    ),
    model=os.environ["OPENAI_MODEL"],
)

async def main() -> None:
    result = await Runner.run(agent, "我想复习 Python 列表，今天只有 20 分钟。")
    print(result.final_output)

if __name__ == "__main__":
    asyncio.run(main())
```

`Agent` 定义角色、指令和模型；`Runner.run` 启动一次任务；`final_output` 是运行器返回的最终输出。没有工具时，这仍只是受指令约束的一次模型流程。若模型编造已经查过的课程或安排，应回到能力边界：没有配置真实查询工具，就不能声称查询成功。

这里把模型 ID 从源码移到环境变量，是为了让同一段代码可以在不同账号和环境里配置；模型名不是密钥。真实 API 调用会产生费用和网络依赖，教学练习时先用小请求，并记录何时调用、何时结束。不要把模型输出直接写入数据库或对外发送。

如果程序提示 `ModuleNotFoundError`，检查当前激活的解释器是否和安装包时相同；如果提示密钥缺失，检查运行进程能否读取环境变量，而不是把密钥硬编码到脚本中。能启动只证明 SDK 导入成功，不代表模型请求、计费权限和网络连接都已验证。

**练习**：删除 `model` 环境变量后观察程序错误，改为在启动前给出清楚配置提示。思考：密钥缺失应由程序在哪里检查？

## 第4章 写出可执行的 Agent 指令

好指令把模糊目标变成可以判断的行为约定。建议至少写清：服务对象、要完成的任务、必须遵守的边界、可用证据、输出结构、信息不足时如何处理。使用可观察的动词，例如“先查课程目录，再按学段过滤”，比“尽可能准确”更有用。

区分三种内容：稳定的角色规则放在 Agent 指令里；每一轮任务放在用户输入里；身份、数据库连接和审计对象等应用状态通过本地上下文传入，不应为了方便把所有内部数据拼进提示词。

避免互相矛盾的要求。例如“永远简短”与“解释每个计算步骤”会争夺优先级；更好的规定是：“默认三点以内；遇到计算题时，展示必要步骤。”指令也应写明拒答和澄清的边界，而不是假设模型总能自行推断。

提示词改变后要用代表性案例重跑。至少覆盖正常请求、缺信息请求、越权请求、边界输入和恶意文本。一次成功示例不能证明规则可靠。

当输出要交给程序继续处理时，定义结构比解析自然语言可靠。例如课程推荐可要求 `title`、`reason` 和 `source_ids`，再由应用确认这些 `source_ids` 真实存在。Agents SDK 可通过 Pydantic 模型设置 `output_type`；结构化输出解决格式一致性，不证明字段内容为真。

SDK 还可以把本地上下文和依赖传入运行，但不发给模型，例如已认证用户 ID、数据库客户端和日志对象。应用上下文与模型上下文是两个边界：前者给程序做权限判断，后者是模型可见的输入。只把回答当前问题必需的信息放进模型上下文。

**练习**：把“给我一个学习建议”改成包含目标、时长、当前水平、输出结构与缺信息处理的任务说明；再写一个反例，检查 Agent 是否会无根据地假设年级。

## 第5章 工具：把可执行能力切成窄接口

工具是普通程序函数或已配置的外部能力。模型提出工具名称和参数；应用执行函数并返回结果。工具说明会影响模型何时调用它，因此名称要描述动作，参数要表达必要输入，返回值要清楚说明成功、未找到和失败的区别。

```python
from agents import Agent, Runner, function_tool

LESSONS = [
    {"title": "列表入门", "topic": "Python 数据结构", "stage": "JUNIOR"},
    {"title": "循环练习", "topic": "Python 控制流程", "stage": "JUNIOR"},
]

@function_tool
def search_lessons(keyword: str) -> str:
    """按关键词检索当前样例课程目录，只返回标题和主题。"""
    matches = [
        lesson for lesson in LESSONS
        if keyword.casefold() in (lesson["title"] + " " + lesson["topic"]).casefold()
    ]
    if not matches:
        return "没有找到匹配课程。"
    return "\n".join(f"{item['title']}｜{item['topic']}" for item in matches)

agent = Agent(
    name="课程目录助手",
    instructions="先使用课程搜索工具，再根据工具返回内容回答。不要编造目录中不存在的课程。",
    tools=[search_lessons],
)
```

这个例子的数据只在进程内，不能代表 K12 数据库。真实工具还要做身份认证、学段与数据归属过滤，并让模型只拿到完成当前任务所必需的字段。

每个参数都要验证：长度、类型、范围、允许值和关联对象。模型生成参数并不代表参数可信。只读搜索工具通常比能修改数据库或发送消息的工具风险低；高影响操作应分成“预览变更”和“确认执行”两个阶段。

工具设计可以按契约逐项检查：名称是否直接表达动作；描述是否说明何时使用；参数是否最少且有范围；返回值是否结构清楚；失败是否可识别；执行是否记录调用者和结果。返回“没有找到匹配项”与返回空字符串不是一回事，前者能让 Agent 给出准确后续说明。

数据库搜索工具应在服务端进行用户归属和学段过滤，不要把完整表内容交给模型后再要求它“只看有权限的行”。只读与写入工具分开；写入工具可接受经过验证的业务对象 ID，而不是任意 SQL 或 shell 文本。

**练习**：设计一个 `get_lesson_detail(lesson_id)` 工具。列出它必须验证的权限，说明为什么不应让模型直接传任意 SQL。

## 第6章 工具循环、结果与失败处理

一次 Agent 运行可能包含多次模型调用和工具执行。可把运行过程理解为：准备输入、调用当前 Agent、检查输出、执行工具或切换专家、继续迭代，直到产生最终回答、到达轮数限制、等待批准或发生错误。一次 `Runner.run` 不等于一次模型调用。

运行结果除了最终回答，还可能包含历史、最后一个 Agent、工具过程或可恢复状态。日志应区分“工具请求已提出”“函数已执行”“外部系统已确认成功”。只有最后一项才能证明操作真正完成。

常见失败包括 API 网络问题、限流、模型输出无法满足结构、工具参数验证失败、工具本身超时，以及达到最大运行轮数。错误要有分类和处理策略：可重试的短暂网络错误、需要用户修正的输入错误、必须停止的权限错误不可混为一谈。自动重试前要确认工具是否幂等，避免重复扣款或重复创建记录。

设置合理的运行预算和最大轮数。Agent 陷入“查一次、再查一次”的循环时，应记录工具调用数和理由，分析是否工具返回不完整、指令冲突或停止条件含糊。

对暂时失败的服务设置超时和有限重试，并向上层返回有分类的结果。网络重试常见于只读请求；对创建、发送、扣费等非幂等操作，先用唯一请求 ID 或幂等键保护重复调用。不能确定前一次是否成功时，先查询最终状态，不要直接再执行一次。

流式输出还要区分“正在生成”和“运行已经结束”。界面可以显示进度，但在最终事件前不要写入“完成”。如果用户取消任务，系统应明确记录取消状态；继续同一任务与创建新的用户请求不是一回事。

**练习**：给课程搜索工具加入无效关键词处理、空结果和模拟超时，决定哪些情况可以重试，哪些情况应该直接向用户说明。

## 第7章 多轮状态与记忆

多轮对话必须明确状态放在哪里。常见策略有：由应用保存可回放的历史；使用 SDK Session 管理多轮；通过 Responses 的 conversation ID 持续状态；或用上一轮的响应 ID 继续。一次会话最好选定一种主要策略，混合回放历史和服务端 continuation 可能重复上下文。

短示例可以用内存会话，但进程退出后数据会消失。需要本地持久化时，Agents SDK 提供 `SQLiteSession`：

```python
import asyncio
from agents import Agent, Runner, SQLiteSession

agent = Agent(name="复习助手", instructions="用清晰步骤回答学习问题。")
session = SQLiteSession("student-demo-01")

async def main() -> None:
    first = await Runner.run(agent, "什么是列表？", session=session)
    print(first.final_output)
    second = await Runner.run(agent, "给一个生活例子。", session=session)
    print(second.final_output)

if __name__ == "__main__":
    asyncio.run(main())
```

生产环境中，学生记忆应有明确目的、最少字段、保留期限和删除方式。对话历史不是可靠的业务数据库；成绩、权限和课程发布状态应从权威业务服务读取，而非相信模型回忆。

同一个浏览器页面里的两个学生不能共享 `session_id`。会话标识必须和已认证用户绑定，服务器在继续运行前重新验证归属。持久会话应定义清除方式；会话日志可能包含学生提问、个人偏好或敏感信息。

不要把所有历史无限追加进每次提示词。过长上下文会增加费用、延迟和旧信息冲突；根据任务保留必要摘要、事实来源和最近对话。若摘要失去来源定位，就可能把模型以前猜测的内容误当成用户确认的事实。

**练习**：比较内存会话和 SQLite 会话的程序重启行为；设计一个只保存“偏好使用图示解释”的用户记忆字段，并说明如何清除它。

## 第8章 多 Agent：交接还是作为工具

把流程拆给多个 Agent 有两种常见模式。交接（handoff）把当前分支交给专家，由专家继续负责面向用户的回答；Agent-as-tool 则由主 Agent 调用一个专家作为工具，主 Agent 保留最终回复责任。

选择取决于输出责任：需要换一个专门角色接管时用 handoff；专家只需完成摘要、分类或校验，而主流程还要汇总时用 Agent-as-tool。拆分边界应由不同权限、工具、指令或负责人来证明，而不是按章节或品牌名随意拆开。

一个“课程分流”流程可以由入口 Agent 判断请求属于概念解释还是学习规划，再交给窄职责专家。每个专家都应有简短的交接说明，主流程应能处理“没有匹配专家”和“专家失败”的情况。专家之间传递的数据也要有结构与权限过滤。

多 Agent 会增加模型调用、延迟、成本、提示词和追踪复杂度。先让一个 Agent 在清晰工具边界内完成任务；只有评估数据证明拆分能提升准确率、隔离权限或便于维护时再扩展。

用 handoff 时，交接说明要说清专家负责什么、主 Agent 何时交出控制权；用 Agent-as-tool 时，工具名与描述要说清专家返回什么。路由结果要测试模糊请求、多个类别、没有合适专家、专家失败以及用户中途补充信息。

专家不要重复相同的大段背景，也不要持有主流程不需要的全部工具。把需要的数据通过结构化参数传递，并按实际工作过滤历史。权限边界应由工具和应用强制执行，不能只依赖专家提示词。

**练习**：为“解释知识点并生成五道练习题”画两种结构：两个专家互相交接；一个主 Agent 调用题目生成专家。比较谁负责最终回答。

## 第9章 Guardrails 与人工审批

Guardrails 用程序检查输入、输出或工具行为；人工审批用于暂停需要人做决定的操作。自动检查适合格式、边界和策略；审批适合有外部副作用的敏感操作。两者不能互相替代。

输入检查可以阻止不允许的请求进入主流程；工具检查可核对用户是否有权访问某门课程；输出检查可发现格式错误或不应外发的内容。对具有副作用的工具，权限校验应靠近实际执行代码，不能只依赖 Agent 指令。

审批是一次暂停的运行：程序检查中断信息，展示给有权审批的人，批准或拒绝后再从同一运行状态恢复。不要把暂停误当作一次成功完成，也不要批准后重新从头启动同一操作。恢复状态应安全保存并绑定用户、操作和过期时间。

对学生作品尤其要控制文件、网络、命令执行和外部服务权限。默认只读、按最小权限开放；需要写入时先展示将改变的内容，再让用户确认。工具超时、审批服务不可用或身份不清楚时，应停止而不是以成功状态返回。

Guardrail 也可能误拦或漏拦，所以要度量两种错误：不应拦截的请求被拦了多少；应拦截的请求漏过多少。为规则准备正常、边界和恶意样例。输入 Guardrail 不是授权系统，最终对象访问仍须由业务服务验证。

审批界面应显示将执行的动作、目标对象、调用者、模型给出的理由和不可逆影响。审批人要能拒绝；拒绝后不能再由模型换个工具绕过。记录审批结果与执行结果，便于之后查明“批准了什么、到底发生了什么”。

**练习**：为“把学习计划写入日历”画出检索、生成预览、用户确认、权限检查、写入和结果核验六步，并指出每一步失败时的状态。

## 第10章 MCP、数据源与沙箱边界

MCP 是连接 Agent 与外部工具、资源的一种协议，不会自动让数据可信。MCP 服务可能拥有自己的身份、网络和权限边界；本地运行时、托管工具与第三方服务的信任方式不同。上线前要明确每个连接能看什么、能改什么、凭什么身份访问。

沙箱解决的是执行环境隔离，例如文件、命令、包和网络；它不等于 Agent 必须使用的功能。仅回答概念问题时不需要 shell。若要操作项目文件，应限制目录、命令与网络，禁止把真实凭证挂进模型可读环境。挂载的私有数据也要遵循最小范围原则。

工具返回内容可能包含恶意指令。把网页、文档、代码注释和工具输出视为待分析的数据，而非授权来源。系统指令、用户目标和外部内容要分层；即使文档要求“忽略之前规则”，也不能让它改变应用策略。

连接外部数据时，记录来源、时间、数据范围和返回结构。不要在 Agent 代码里直接开放通用网络访问；按任务提供有限工具，例如只查询课程目录或只读指定域名。凭证由应用或连接管理器持有，不应作为提示词内容或工具返回值发给模型。

沙箱降低执行带来的影响范围，但不能自动保证安全。仍要限制 CPU、内存、时间、磁盘和网络；不要把任意学生上传文件与高权限凭证放在同一执行环境。对生成文件做格式与大小检查后，再允许用户下载或进入其他服务。

**练习**：假设一个 MCP 工具能读学生作业、另一个能发布作业成绩。分别写出所需权限、审批点、审计字段和失败关闭策略。

## 第11章 观测与评估：从“看起来不错”到可比较

Trace 将一次完整运行中的模型调用、工具调用、handoff、guardrail 和自定义步骤串起来。调试应先抽取代表性运行，按时间线确认模型选了哪个工具、实际参数是什么、工具返回了什么、最后输出如何形成。若只记录最终回答，就很难定位路由、权限或工具错误。

先建立一组小型评估数据：正常请求、空结果、信息不足、越权请求、恶意资料、服务失败和边界值。定义可判断的评分标准，例如是否选择正确工具、是否引用真实检索结果、是否泄露不必要字段、是否在应审批时暂停。用固定数据重跑新旧提示词，才能比较改变有没有退步。

监控的指标包括成功率、工具错误率、平均工具调用数、延迟、人工审批比例和单位请求成本。指标需要按任务类型分组；所有类型合在一起的平均值可能掩盖某类高风险失败。

不要把“模型回答流畅”当成正确性评估。高影响任务需要有事实来源、结构化校验、权限边界、人工监督和失败恢复。

建立基线后再改提示词。保留一组固定样例和评分标准，每次改动都记录版本、模型、数据集、运行时间与结果。先通过 Trace 看某一次错误如何产生，再用数据集检查问题是否普遍。人工点评适合发现新问题，自动评分适合重复比较；两者不能互相替代。

成本和延迟也是质量的一部分。记录平均模型调用次数、工具调用次数、失败重试和人工审批比例。若一个多 Agent 版本只提高很少准确率，却把延迟和成本大幅提高，就要重新评估架构。

**练习**：为课程搜索 Agent 写五条评估样例，其中至少一条应要求拒绝越权访问。为每条定义“通过”的可观察条件。

## 第12章 综合项目：课堂资料问答助手

项目目标：学生提出课程问题，助手只在允许范围内查询课程资料，并给出带证据的解释。先不用公网搜索、写文件或改成绩；一个本地只读工具就足以验证核心流程。

推荐结构：`agent.py` 定义 Agent 与指令；`tools/course_search.py` 实现只读搜索；`policy.py` 验证学段与所有权；`schemas.py` 定义结构化返回；`tests/` 放入预期案例。工具返回课程 ID、标题、章节和来源定位，不返回无关学生信息。Agent 基于结果作答，不得把未检索到的内容描述成数据库事实。

按小步交付：先跑通一次无工具回答；再添加假数据只读搜索；为无结果添加解释；加学段过滤；加入越权案例；最后记录 trace 并跑固定评估集。每次改变一个边界，失败时检查输入、工具参数和返回结果，不要先增加更多 Agent。

项目验收条件：所有课程查询在服务器端过滤；未知课程不能被猜测打开；空结果会明确说明；外部文本按不可信数据处理；工具异常不会伪装成功；敏感写操作不存在或需要独立审批；评估样例可以重复运行。

首个原型可以只支持三种意图：解释概念、搜索课程、生成练习提纲。每个意图对应清晰的输出契约；“搜索课程”必须调用只读目录工具；“生成练习”不能把答案或隐藏评分标准返回给学生。若用户请求超出三种能力，助手应坦白说明边界或提出澄清问题。

交付前做一次威胁建模：学生能否通过构造章节 ID 读到别的学段？工具返回的教师备注会不会传到学生端？Agent 是否能自行升级权限？失败重试会不会重复写入？这些问题应由服务端测试和权限检查证明，而不是由提示词承诺解决。

继续扩展前先问：用户问题是否真的需要新工具？新工具是否有明确权限边界？增加一次模型调用能否由评估结果证明值得？
