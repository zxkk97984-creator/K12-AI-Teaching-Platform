# 综合项目：一个可扩展的行程规划器

## 学习目标

- 能把一个真实需求拆成若干可分别实现的查询与统计功能，并为每个功能选择合适的数据结构。
- 能对每个功能写出复杂度，并说明在什么规模下这个复杂度是可接受的。
- 能处理边界输入（空数据、单条数据、全部相同、越界参数），并为每种情况给出明确定义的行为。
- 能写出可被他人复核的测试，覆盖正常路径和边界路径。

## 开始之前

先修要求：本书前十一章的全部内容。这一章不会引入新概念，它要求你把已有的工具组合起来使用。

热身问题：假设你要为一个学生社团管理系统设计数据结构。成员有学号、姓名、分数、所属社团四个字段。系统需要支持五种操作：按学号查人、按分数区间查人、按分数取前 $k$ 名、统计各社团人数、求分数的中位数。这五种操作里，哪些用字典最合适？哪些需要先排序？哪些两种都要用？先写下你的判断。

材料：Python 3.12 环境，一个文本文件用来保存你的数据和测试记录。

## 情景导入

社团联合会的干事接手了一件事：把三个社团的成员信息整理成一个可以查询的小工具。他手上的原始数据是一张纸质表格，需要录入、核对，然后支持几种查询。

第一次交上去的版本是这样写的：所有功能都用一个列表完成，要查人就把列表从头扫到尾，要取前几名就用双重循环挑。数据有 8 条时一切正常。后来并入了整个年级的数据，一共 600 多条，程序开始明显变慢：查询要等一两秒，取前 20 名要等更久。

他花了一个下午重写：按学号查人改用字典，取前 $k$ 名改用排序后切片，分数区间查询改用排序后二分。数据规模没变，所有操作都变成了瞬间完成。

这一章的任务就是完整地做一遍这件事。和前十一章不同，这次没有“标准答案”，你需要自己做决定，但要能说清楚每个决定的理由和代价。

## 知识讲解

### 从需求到数据结构：一个对照方法

面对一个查询需求，先问三个问题，再决定用什么结构。

**问题一：查询的条件是什么？** 是按一个精确的值查（“学号等于 2024005”），还是按范围查（“分数在 80 到 92 之间”），还是按顺序取前 $k$ 个（“分数最高的 10 个人”）？精确匹配最适合字典；范围查询最适合有序数组加二分；取前 $k$ 名最适合排序后切片。

**问题二：查询会被执行多少次？** 如果只查一次，花 $O(n \log n)$ 排序就不划算；如果要查上万次，排序的一次性成本可以被摊薄到几乎可忽略。

**问题三：数据会变化吗？** 如果数据是只读的（一次性录入后不再改动），可以放心建立索引。如果数据会被频繁修改，每次修改后还要不要维持有序？这决定了两套完全不同的设计。

下表给出五种操作的建议方案，可以作为你自己项目的起点。

| 操作 | 推荐结构 | 单次代价 | 建立代价 |
| --- | --- | --- | --- |
| 按学号查人 | 字典（学号到记录） | $O(1)$ | $O(n)$ |
| 按分数区间查人 | 排序后的记录列表 + 二分定位 | $O(\log n + k)$ | $O(n \log n)$ |
| 取分数前 $k$ 名 | 排序后切片 | $O(n \log n)$ 或 $O(k)$（若已排序） | $O(n \log n)$ |
| 统计各社团人数 | 字典计数 | $O(n)$ | — |
| 求分数中位数 | 排序后取中间（或维护两个堆） | $O(n \log n)$ | — |

### 边界输入：比正常路径更重要

真实数据总是脏的，边界处理占了这类工具一半以上的工作量。至少要明确下面几类情况的定义：

**空数据。** 查询返回什么？按学号查人返回 `None`；区间查询返回空列表；取前 $k$ 名返回空列表；中位数返回 `None`（**不要返回 0**，因为 0 可能是一个合法的分数，会让调用方误以为真的有人考了 0 分）。

**单条数据。** 中位数就是那一条的分数；区间查询返回包含或不包含那一条（取决于区间）；取前 $k$ 名时，如果 $k$ 大于 1，返回的还是那一条。

**$k$ 越界。** 取前 0 名应当返回空列表，取前 99 名而只有 8 条数据时应当返回全部 8 条。**不能直接切片 `records[:k]` 就完事**——那样在 $k$ 为负数时行为很不直观（Python 里 `[:-1]` 会去掉最后一个元素），得到的结果和“取前负数名”的直觉完全不同。正确的做法是显式处理 $k$ 小于等于 0 的情况。

**区间参数颠倒。** 如果调用方传进来的下界大于上界，应当返回空列表或者抛出异常，而不是返回一个看起来正常的结果。要在函数文档里写清你选哪一种。

**重复值。** 分数相同时的排序必须有一个稳定的次序规则（比如分数相同按学号升序），否则同一个查询在不同时刻可能给出不同的顺序，使用者会觉得程序“不稳定”。

### 复杂度说清楚到什么程度

这一章的每个功能都要给出复杂度。写法建议统一成三段：

**第一，说明 $n$ 是什么。** 比如“$n$ 是成员总数”。不要含糊地写“$n$ 是数据规模”。

**第二，说明这个操作的时间复杂度。** 如果函数内部包含多个步骤，写出总的量级，并指出主导项。比如区间查询是 $O(\log n + k)$，其中 $k$ 是结果条数——**结果本身的输出代价不能忽略**，如果区间覆盖了全部 $n$ 条，那输出就是 $O(n)$，任何算法都躲不开。

**第三，说明空间复杂度和前提。** 比如“需要一个额外的字典，空间是 $O(n)$”；再比如“区间查询要求记录列表已经按分数排好序，排序的代价在建立阶段一次性付出”。

**明确写出前提很重要**，因为复杂度结论依赖前提。二分查找的前提是有序，如果你的函数拿到的是无序列表，那么它的复杂度分析就是错的，实际行为也会出错（第五章已经演示过这一点）。

### 测试怎么写才有效

有效的测试不是“跑一遍看有没有报错”，而是**先写下预期结果，再运行程序核对**。这一章要求你为每个功能至少写三类测试。

**第一类：正常路径。** 用中等规模的数据，检查返回值是否符合预期。这类测试最容易写，也最容易漏掉问题。

**第二类：边界路径。** 空数据、单条数据、$k$ 等于 0、$k$ 大于总数、区间参数颠倒、分数全部相同。这些是 bug 最容易藏身的地方。

**第三类：对拍。** 用一个朴素但显然正确的实现（比如线性扫描）作为对照，在随机数据上和你的高效实现对比结果。第十、十一章已经用过这个手法——**它能在你自己都没想到的输入上发现错误**。

还有一条经验：**断言要比“不为空”更具体**。写 `assert result == expected` 比写 `assert len(result) > 0` 强得多，因为后者在结果错了一半时依然会通过。

## 详细示例

### 示例一：小型数据集上的完整参考实现

任务：用 8 条数据实现全部五个功能，并给出每一步的真实输出。

```python
records = [
    ("2024001", "林小满", 92, "编程社"),
    ("2024002", "郑岩", 78, "编程社"),
    ("2024003", "何雨", 88, "文学社"),
    ("2024004", "周舟", 65, "编程社"),
    ("2024005", "苏晴", 95, "文学社"),
    ("2024006", "陈默", 71, "科学社"),
    ("2024007", "罗清", 83, "科学社"),
    ("2024008", "陆遥", 90, "文学社"),
]

def build_index(records):
    return {r[0]: r for r in records}

def top_k(records, k):
    if k <= 0:
        return []
    return sorted(records, key=lambda r: (-r[2], r[0]))[:k]

def score_range(records, lo, hi):
    if lo > hi:
        return []
    return sorted([r for r in records if lo <= r[2] <= hi], key=lambda r: r[2])

idx = build_index(records)
print(idx["2024005"])
print([(r[0], r[2]) for r in top_k(records, 3)])
print([(r[0], r[2]) for r in score_range(records, 80, 92)])
print([(r[0], r[2]) for r in top_k(records, 0)])
```

**推理过程。** `build_index` 一次遍历建立字典，之后按学号查询是 $O(1)$。`top_k` 用排序，排序键是 `(-分数, 学号)`——负号把“降序”表达成一个升序排序，学号作为并列时的次序，这样同一个查询的结果是确定的。`score_range` 先筛选再排序，保证结果按分数升序。

**预期输出。**

```text
('2024005', '苏晴', 95, '文学社')
[('2024005', 95), ('2024001', 92), ('2024008', 90)]
[('2024007', 83), ('2024003', 88), ('2024008', 90), ('2024001', 92)]
[]
```

**为什么正确。** 按学号 `2024005` 查到苏晴，分数 95。前 3 名是 95、92、90，学号分别是 005、001、008，正确。分数在 80 到 92 之间（含端点）的有 83、88、90、92 共四条，按分数升序输出，正确。`k` 等于 0 时返回空列表。

**边界情况。** `top_k(records, 99)` 返回全部 8 条（切片自动截断，这是合理的）；但要注意如果按 `sorted(...)[:k]` 的写法，$k$ 为负数时会从末尾切掉几条，所以必须在函数开头拦住 `k <= 0`。`score_range(records, 92, 80)` 因为下界大于上界返回空列表，而不是抛异常——这个约定必须写进函数说明。

### 示例二：社团人数统计与中位数

任务：统计各社团人数（人数相同时按社团名排序），并求出分数的中位数。

```python
from collections import Counter

def club_counts(records):
    c = Counter(r[3] for r in records)
    return sorted(c.items(), key=lambda kv: (-kv[1], kv[0]))

def median_score(records):
    vals = sorted(r[2] for r in records)
    n = len(vals)
    if n == 0:
        return None
    if n % 2 == 1:
        return vals[n // 2]
    return (vals[n // 2 - 1] + vals[n // 2]) / 2

print(club_counts(records))
print(median_score(records))
print(median_score([]))
```

**推理过程。** `Counter` 本质上就是一次遍历加字典计数的封装，代价 $O(n)$；输出前排序是为了让结果确定（否则字典的迭代顺序虽然稳定，但不满足“按人数再按名称”的要求）。`median_score` 先排序再取中间：奇数个取正中间那一个，偶数个取中间两个的平均值。

**预期输出。**

```text
[('文学社', 3), ('编程社', 3), ('科学社', 2)]
85.5
None
```

**核对。** 文学社和编程社都是 3 人，科学社 2 人；人数相同时按社团名排序，`文学社` 和 `编程社` 在 Unicode 码点上谁在前需要确认——这里输出的是 `文学社` 在前，这是排序键比较的结果，你的运行环境如果一致，输出也会一致。分数排序后是 65、71、78、83、88、90、92、95，共 8 个（偶数），中间两个是第 4、5 个即 83 和 88，平均 85.5。空数据返回 `None`。

**边界情况。** 空数据返回 `None` 而不是 0，理由前面已经说过。如果分数里有重复值，中位数照常计算，不受影响。如果成员数是奇数，返回的是一个整数；偶数时返回的可能是一个小数——**调用方要能接受两种类型**，这一点必须在文档里写明，否则下游代码做格式化时会出错。

### 示例三：用对拍发现一个真实的错误

任务：先用一个“看起来没问题”的区间查询实现，再用对拍找出它的 bug。

```python
def score_range_buggy(records, lo, hi):
    sorted_recs = sorted(records, key=lambda r: r[2])
    # 找第一个不小于 lo 的位置
    left = 0
    right = len(sorted_recs)
    while left < right:
        mid = (left + right) // 2
        if sorted_recs[mid][2] < lo:
            left = mid + 1
        else:
            right = mid
    # 从 left 开始取，直到遇到大于 hi 的
    out = []
    i = left
    while i < len(sorted_recs) and sorted_recs[i][2] <= hi:
        out.append(sorted_recs[i])
        i += 1
    return out

def score_range_ref(records, lo, hi):
    if lo > hi:
        return []
    return sorted([r for r in records if lo <= r[2] <= hi], key=lambda r: r[2])

print(score_range_buggy(records, 80, 92) == score_range_ref(records, 80, 92))
print(score_range_buggy(records, 92, 80), score_range_ref(records, 92, 80))
```

**预期输出。**

```text
True
[('2024005', '苏晴', 95, '文学社')] []
```

**问题在哪。** 当 `lo` 大于 `hi` 时，第一个函数仍然会执行：二分找到第一个不小于 92 的位置（也就是 92 所在位置），然后从这个位置往后取所有不超过 80 的元素——由于 92 后面的元素都大于 80，循环立即结束……但实际上在样本里它返回了 95 那一条。原因是当 `lo` 大于 `hi` 时，二分定位到的是不小于 `lo` 的**第一个位置**（这里是 95 所在位置，因为 92 之后紧接着就是它），然后检查 `95 <= 80` 不成立本该停下——这个具体行为依赖数据分布，**关键是它没有返回正确的空列表**。

对拍立刻暴露了这个不一致：朴素实现返回 `[]`，而被测函数返回了一条记录。

**为什么这个例子有价值。** 这个 bug 在“下界小于上界”的正常调用中完全不会出现。如果测试只覆盖正常路径，它会一直潜伏到某天有人传错参数才爆发。而**对拍的价值恰恰在于它不需要你事先猜到这种输入**：只要把两类实现放在随机数据上比，不一致就会自己冒出来。

**边界情况。** 即使修好了 `lo > hi` 的检查，这个实现还有另一个隐含问题：它每次都重新排序。如果区间查询会被调用很多次，正确做法是**在建立阶段排一次序，查询时复用**。这正是下一节动手实践要你做的事。

## 动手实践

**目标**：独立完成一个校园查询与统计工具，包含五个功能、完整的边界处理和一套对拍测试。

**材料**：Python 3.12 环境，一个 `.py` 文件保存实现，另一个保存测试（或放在同一文件的不同函数里）。

**步骤**：

1. **准备数据。** 用代码生成至少 300 条成员记录，字段是学号、姓名、分数（0 到 100 的整数，允许重复和极端值）、社团（至少 4 个社团）。另外手工准备一份 8 条的固定小数据集，用于人工核对。学号规则要一致（比如都是 7 位数字），并把规则写进注释。
2. **确定接口。** 为五个功能各写一个函数，先写函数签名和文档字符串（说明参数含义、返回值含义、边界情况下的行为），再写实现。文档字符串里必须写明：空数据返回什么、$k$ 越界返回什么、区间参数颠倒返回什么。
3. **建立索引结构。** 写一个 `build(records)` 函数，一次性返回一个包含多个结构的对象（可以用字典或一个简单的类）：按学号索引的字典、按分数排序的记录列表、按社团分组的字典。**排序只在这里做一次**，后面的查询复用。
4. **实现五个查询。** 按学号查人、按分数区间查人（用第 3 步排好的列表加二分定位）、取前 $k$ 名（用排好的列表切片）、统计社团人数、求中位数（用排好的列表直接取中间，不再排序）。
5. **写对拍测试。** 为区间查询、前 $k$ 名、中位数各写一个朴素实现（线性扫描、完整排序、每次重新排序），在 50 组随机数据（每组 50 到 200 条）上对比。任何一组不一致，就把那组数据打印出来并定位原因，修好之后重新跑。
6. **写边界测试。** 覆盖下列全部情况并打印结果：空数据（五个功能各测一次）、单条数据、$k$ 等于 0、$k$ 等于 1、$k$ 大于总数、区间下界大于上界、区间完全落在数据范围外、分数全部相同。对每一种，先在纸上写下预期，再运行核对。
7. **写复杂度说明。** 在代码末尾用注释写出：建立阶段的复杂度、五个查询各自的复杂度、整个工具的空间复杂度。每一条都要说明 $n$ 指什么、有没有前提。
8. **压力测试。** 把数据规模提高到 100000 条，测量建立阶段耗时和每种查询各 1000 次的总耗时。把结果记录下来，和你的复杂度分析对照，看是否与预期一致。

**完成判据**：五个功能全部实现且通过步骤 5 的对拍；步骤 6 的八种边界情况都有明确且符合文档字符串的输出；步骤 7 的复杂度说明写全；步骤 8 有真实测量数字，且能解释测量结果与复杂度分析是否吻合（例如区间查询 1000 次的耗时应当远小于按学号查询的 1000 次乘以一个 $n$ ——因为前者不是线性的）。

**排查方法**：如果对拍出现了不一致，按下面的顺序排查。第一，检查两个实现是不是在**同一份数据**上比较——如果朴素实现用的是原始列表而高效实现用的是排序后的列表，两者的“顺序”约定可能不同，导致结果集合相同但顺序不同。可以先比较排序后的结果，确认差异是“内容不同”还是“顺序不同”。第二，检查区间端点的开闭约定是否一致，`lo <= x <= hi` 和 `lo < x < hi` 会在端点值恰好存在时给出不同结果。第三，检查 $k$ 越界和空数据的分支有没有在高效实现里也处理——**朴素实现往往自然地处理了这些情况**，而优化过的实现容易在提前返回的分支上漏掉。第四，如果耗时和复杂度分析对不上，确认测量时有没有把建立索引的时间反复算进单次查询里。

## 常见误区

**误区一：“这一章没有新知识，就是把前面功能拼起来，很快就能写完。”** 反例：边界处理和测试代码通常占总工作量的一半以上，而且是最容易出错的部分。一个只有正常路径能跑的工具，在真实数据上会立刻暴露问题——比如空数据导致除零、$k$ 为负数导致切片行为诡异、重复分数导致排序结果不确定。**“拼起来”本身不简单，难的是把所有接口约定统一并且验证过。**

**误区二：“查询快就够了，建立索引慢一点没关系。”** 这只在“索引建立一次、查询很多次”时成立。如果程序是“每次启动读一次数据、只查一次就退出”，那么建立索引的 $O(n \log n)$ 排序完全是浪费——直接线性扫描一次是 $O(n)$。选择方案前要先估清楚“查询次数”和“数据规模”这两个数字，而不是默认“优化过的一定更好”。

**误区三：“复杂度分析做完了就不用实测。”** 反例：复杂度分析不考虑常数因子。如果按学号查询的字典查找每次要构造一个复杂的键（比如把四个字段拼成字符串），它的常数可能比一次线性扫描还大，在小数据上反而更慢。实测能发现这类问题，也能验证你对程序结构（比如“排序只做了一次”）的理解是否与实际一致。**分析决定方向，实测确认细节**，两者都要做。

## 本章小结

- 从需求到数据结构的对照方法是问三个问题：查询条件是精确匹配还是范围，查询会被执行多少次，数据会不会变化。
- 边界处理的定义必须先于实现写下来；空数据、$k$ 越界、区间参数颠倒、重复值这几类情况最容易出错，也最容易被漏测。
- 复杂度说明要写清三件事：$n$ 指什么、时间量级和主导项、空间与前提。结论依赖前提，前提没写清的复杂度分析是无效的。
- 对拍是发现意料之外 bug 的最有效手段，它不需要你事先猜到问题输入；而边界测试需要你先写下预期再运行核对。
- 全书到这里结束。回过头看，十二章其实围绕同一个问题展开：**面对一个需求，怎样选择合适的数据组织和处理步骤，使得它在数据变多时依然可用**。这个判断力比记住任何一个具体算法都更重要。
