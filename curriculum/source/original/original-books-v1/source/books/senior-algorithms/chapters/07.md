# 递归与分治

## 学习目标

- 能写出一个递归函数，并说明它的终止条件和递推关系分别是什么。
- 能用手工展开的方式追踪递归调用，画出调用树，并据此解释重复计算的来源。
- 能识别能用记忆化优化的递归，并说明优化前后的复杂度差别。
- 能说出递归深度带来的两个实际限制，以及把它们转化为循环的一般方法。

## 开始之前

先修要求：会写函数、理解函数调用可以返回值、能读懂第六章的归并排序（它已经用过递归）。

热身问题：斐波那契数列的定义是 $F(0)=0$，$F(1)=1$，$F(n)=F(n-1)+F(n-2)$。如果直接把这个定义写成程序，计算 $F(30)$ 大约要做多少次函数调用？本章第二节会给出实测数字，先猜一个量级。

材料：Python 3.12 环境。

## 情景导入

信息学小组接了一个任务：把一个盘子大小各不相同的塔从 A 柱搬到 C 柱，规则是每次只能移动一个盘子，大盘子不能压在小盘子上，还有一个可以借用 B 柱。

组里两位同学的处理方式完全不同。一位同学试图列出所有移动顺序，写了十几行条件判断，到四个盘子时就开始出错。另一位同学只写了六行代码：

```python
def hanoi(n, src, dst, via, moves):
    if n == 0:
        return
    hanoi(n - 1, src, via, dst, moves)
    moves.append((src, dst))
    hanoi(n - 1, via, dst, src, moves)

moves = []
hanoi(3, "A", "C", "B", moves)
print(len(moves))
print(moves)
```

六个盘子、十个盘子，他的程序照样能算，只是调用次数越来越多。而那位写条件判断的同学到现在还没把四个盘子的情况写对。

为什么有的人用递归几行就解决了，有的人用循环怎么都理不清？递归到底在想什么？本章要把这件事说清楚，包括递归什么时候好用、什么时候会拖慢程序甚至让程序崩溃。

## 知识讲解

### 递归的两个要素

递归函数是**在自己的定义里调用自己**的函数。要让这样的定义有意义，必须同时具备两件事。

**第一，终止条件（也叫基线条件）。** 必须存在一种情况，函数不再调用自己，直接返回结果。如果缺少终止条件，函数会一直调用下去，直到耗尽调用栈而报错。

**第二，递推关系。** 除了终止条件之外的情况，必须能表示为“规模更小的同类问题”加上一些额外工作。而且这个规模必须**确实在变小**，否则永远到不了终止条件。

用阶乘举例：

```python
def fact(n):
    if n <= 1:
        return 1
    return n * fact(n - 1)

print([fact(i) for i in (0, 1, 5, 10)])
```

**预期输出。**

```text
[1, 1, 120, 3628800]
```

终止条件是 `n <= 1` 时返回 1。递推关系是 $n! = n \times (n-1)!$，规模从 $n$ 降到 $n-1$，每次减 1，必然到达终止条件。`fact(10)` 等于 3628800，与 $10! = 3628800$ 一致。

**终止条件为什么要写成 `n <= 1` 而不是 `n == 1`。** 因为要处理 $n$ 等于 0 的情况：数学上 $0! = 1$，写成 `n == 1` 的话，`fact(0)` 会继续调用 `fact(-1)`、`fact(-2)`……永远到不了基线。写成 `n <= 1` 同时覆盖了 0 和 1，也顺带让负数输入有了一个明确的（虽然不合理但不会死循环的）行为。**边界输入必须由终止条件覆盖，而不是靠调用方保证。**

### 手工追踪：画出调用树

理解递归不能靠“在脑子里模拟”，要靠把调用画出来。以 `fact(4)` 为例，调用过程是层层深入再到层层返回：

```text
fact(4)
  fact(3)
    fact(2)
      fact(1)  → 返回 1
    → 返回 2 * 1 = 2
  → 返回 3 * 2 = 6
→ 返回 4 * 6 = 24
```

这张图叫**调用树**（这里退化成一条链）。注意执行顺序：先一路往下走到基线，再一路往上返回。写成代码时，`return n * fact(n - 1)` 里乘号左边的 `n` 是在**往下走之前**就已经确定的值，右边要等到递归返回才有值。

对于会分叉的递归，调用树才真正有价值。以斐波那契为例：

```python
def fib_naive(n):
    if n <= 1:
        return n
    return fib_naive(n - 1) + fib_naive(n - 2)
```

`fib_naive(4)` 的调用树是：

```text
fib(4)
├── fib(3)
│   ├── fib(2)
│   │   ├── fib(1)
│   │   └── fib(0)
│   └── fib(1)
└── fib(2)
    ├── fib(1)
    └── fib(0)
```

可以数出 `fib(2)` 出现了两次，`fib(1)` 出现了三次，`fib(0)` 出现了两次。**同一件事被反复计算**，这就是斐波那契递归慢的根本原因。

### 重复计算的代价：实测数据

把调用次数直接数出来：

```python
def fib_count(n, counter):
    counter[0] += 1
    if n <= 1:
        return n
    return fib_count(n - 1, counter) + fib_count(n - 2, counter)

for n in (5, 10, 20, 25):
    c = [0]
    v = fib_count(n, c)
    print(n, v, c[0])
```

**预期输出。**

```text
5 5 15
10 55 177
20 6765 21891
25 75025 242785
```

**读表要点。** 每次 $n$ 增加 5，调用次数大约涨 11 倍（177 到 21891 是 123 倍，因为 $n$ 从 10 跳到 20）。这个增长接近 $1.618^n$——黄金比例正是斐波那契的增长率。也就是说，$F(30)$ 大约需要 270 万次调用，$F(40)$ 需要约 3 亿次，$F(50)$ 就完全跑不动了。

### 记忆化：把重复计算变成一次

既然慢是因为重复计算同一个子问题，那就把算过的结果存起来，下次直接查。

```python
def fib_memo(n, memo=None):
    if memo is None:
        memo = {}
    if n in memo:
        return memo[n]
    if n <= 1:
        return n
    memo[n] = fib_memo(n - 1, memo) + fib_memo(n - 2, memo)
    return memo[n]
```

同样的调用计数方式，结果是：

| $n$ | 朴素递归调用次数 | 记忆化后调用次数 |
| --- | --- | --- |
| 10 | 177 | 19 |
| 25 | 242785 | 49 |
| 35 | （约 3000 万） | 69 |

**读表要点。** 记忆化后 $n$ 从 10 涨到 35，调用次数从 19 涨到 69，几乎线性增长（约每个 $n$ 加 2 次）。这是因为每个 $n$ 只被真正计算一次，其余访问都直接命中缓存。复杂度从指数级 $O(1.618^n)$ 降到线性级 $O(n)$。

**记忆化的两个前提。** 第一，问题必须有**重叠子问题**——如果子问题之间互不重复，缓存就没有用武之地。第二，函数必须是**纯的**：同样的输入一定得到同样的输出，不依赖外部变化的状态。如果函数依赖会变的全局变量，缓存就会返回过期结果。

用可变对象做默认参数是一个需要小心的写法。上面写的是 `memo=None` 再在函数体内新建字典，而不是直接写 `def fib(n, memo={})`。后者会出问题：Python 的默认参数只在函数定义时求值一次，所以那个字典会被**所有调用共享**，多次调用之间会互相污染。这是 Python 里最著名的陷阱之一。

### 递归的两个实际限制

**第一，递归深度有限。** Python 默认的递归深度上限是 1000 层左右，超过会抛 `RecursionError`。深度 1000 的递归在算法上完全正常，但在这个语言里跑不起来。可以把上限调高（`sys.setrecursionlimit`），但这不是根治办法：真正的限制来自操作系统给进程分配的栈空间，调得太高会在栈溢出时直接崩溃进程，而不是抛出可以捕获的异常。

**第二，每次调用都有额外开销。** 创建栈帧、保存局部变量、传递参数都花时间。在 Python 里，一个简单的递归调用比等价的循环迭代慢好几倍。这不是算法问题（复杂度可能完全相同），而是实现代价。

**把递归转成循环的一般方法**：如果是“链式”递归（像阶乘那样每次只有一个子调用），可以用一个变量在循环里累积，直接换成循环。如果递归是“分叉”的（像斐波那契或树的遍历），通常要用**显式的栈**来模拟调用栈——自己维护一个列表记录“还没处理完的任务”。第八章的树遍历会用到这个方法。

## 详细示例

### 示例一：汉诺塔的移动次数与规律

任务：推导 $n$ 个盘子的最少移动次数，并用程序核对。

**推理过程。** 要把 $n$ 个盘子从 A 移到 C，必须先把上面 $n-1$ 个移到 B（记为 $T(n-1)$ 步），再把最大的那个从 A 移到 C（1 步），最后把 B 上的 $n-1$ 个移到 C（又是 $T(n-1)$ 步）。所以 $T(n) = 2T(n-1) + 1$，且 $T(0) = 0$。

展开这个递推：$T(1) = 1$，$T(2) = 3$，$T(3) = 7$，$T(4) = 15$。规律是 $T(n) = 2^n - 1$。可以用数学归纳法证明：假设 $T(n-1) = 2^{n-1} - 1$，则 $T(n) = 2(2^{n-1} - 1) + 1 = 2^n - 1$，成立。

```python
def hanoi(n, src, dst, via, moves):
    if n == 0:
        return
    hanoi(n - 1, src, via, dst, moves)
    moves.append((src, dst))
    hanoi(n - 1, via, dst, src, moves)

for n in (1, 2, 3):
    m = []
    hanoi(n, "A", "C", "B", m)
    print(n, len(m))
print(hanoi.__name__)
```

**预期输出。**

```text
1 1
2 3
3 7
hanoi
```

**为什么正确。** 移动次数 1、3、7 与公式 $2^n - 1$ 在 $n$ 等于 1、2、3 时的结果 1、3、7 一致。程序没有显式写出任何判断“哪个盘子能移到哪”的条件，但结果必然合法——因为递推过程保证了每次移动都是把“当前最小的一个”从一根柱移到另一根柱，合乎规则。

**边界情况。** $n$ 等于 0 时应当不产生任何移动，程序里 `if n == 0: return` 处理了这一点，`len(moves)` 是 0。这个基线是必需的：如果写成 `if n == 1` 作为基线，$n$ 等于 0 时会继续递归到负数，导致无限递归。另外，$n$ 等于 64 时移动次数是 $2^{64} - 1$，约 $1.8 \times 10^{19}$ 次——即使每秒移动一次，也要几百亿年。**递归的简洁不等于代价低**，这一点在汉诺塔上体现得极其夸张。

### 示例二：递归求最大公约数

任务：用欧几里得算法求最大公约数，并说明为什么它不会很深。

```python
def gcd(a, b):
    if b == 0:
        return a
    return gcd(b, a % b)

print(gcd(48, 18))
print(gcd(17, 5))
print(gcd(100, 0))
```

**推理过程。** 欧几里得算法的依据是：$a$ 和 $b$ 的最大公约数等于 $b$ 和 $a \bmod b$ 的最大公约数。以 48 和 18 为例：48 除以 18 余 12，所以问题变成求 18 和 12 的公约数；18 除以 12 余 6，变成 12 和 6；12 除以 6 余 0，答案是 6。手工核对：48 和 18 的公约数有 1、2、3、6，最大的是 6，正确。

**预期输出。**

```text
6
1
100
```

**为什么正确。** 第二组 17 和 5 互质，返回 1。第三组 `gcd(100, 0)` 中 `b` 已经是 0，直接返回 `a` 等于 100——这是一个必须明确定义的边界：数学上“100 和 0 的最大公约数”约定为 100，程序里的基线正好覆盖了它。

**为什么递归深度很小。** 每层递归里，参数从 $(a, b)$ 变成 $(b, a \bmod b)$，而 $a \bmod b$ 一定小于 $b$，并且可以证明每两次递归至少缩小一半（拉梅定理）。所以深度是 $O(\log(\min(a,b)))$——即使输入是几十位的整数，递归也只有几十层，完全不会触及深度限制。**同样是递归，汉诺塔是线性深度，欧几里得是对数深度，适用性差别很大。** 判断一个递归能不能用，要看它的深度增长趋势，而不是看它“是不是递归”。

### 示例三：递归反转列表，以及它的代价

任务：用递归反转一个列表，并说明为什么这个写法虽然优雅但不实用。

```python
def rev(a):
    if len(a) <= 1:
        return a[:]
    return rev(a[1:]) + [a[0]]

print(rev([1, 2, 3, 4]))
print(rev([]))
print(rev([9]))
```

**预期输出。**

```text
[4, 3, 2, 1]
[]
[9]
```

**推理过程。** 递推关系是“反转整个列表 = 反转去掉首元素后的部分，再把首元素接到末尾”。终止条件是长度不超过 1 时直接返回。

**为什么这个写法不实用。** 每一层递归都做了一次 `a[1:]` 切片，切片会复制 $n-1$ 个元素；总共复制 $n + (n-1) + \cdots + 1 = \frac{n(n+1)}{2}$ 个元素，是 $O(n^2)$。而且递归深度是 $n$，列表长度超过约 1000 时就会触发 `RecursionError`。相比之下，`a[::-1]` 一趟完成，是 $O(n)$ 且深度为 1。

**边界情况。** 空列表返回空列表（不报错），单元素列表返回它自己。这两个边界都正确，说明基线条件 `len(a) <= 1` 覆盖到位。但如果写成 `if not a: return []` 再加一句处理单元素，反而容易漏掉某一支，这也是为什么基线条件应当尽量写得宽一些。

## 动手实践

**目标**：实现三个递归函数，画出调用树，用计数验证复杂度，再改成等价的循环版本并比较。

**步骤**：

1. 实现 `sum_list(a)`，返回列表元素之和。终止条件是空列表返回 0，递推关系是首元素加上剩余部分的和。
2. 在纸上画出 `sum_list([3, 1, 4, 1, 5])` 的完整调用树，标出每一层返回的值。画完后再运行程序核对最终结果。
3. 给 `sum_list` 加一个计数器（用一个单元素列表当可变容器，或者用类的属性），统计不同长度下（5、10、20）的调用次数，填入表格。
4. 实现 `count_ways(n)`：一次可以上 1 级或 2 级台阶，问上 $n$ 级台阶有多少种走法。先写出递推关系和终止条件，再写代码。注意终止条件要覆盖 $n$ 等于 0 和 $n$ 等于 1 两种情况。
5. 用第 3 步同样的方法统计 `count_ways` 在 $n$ 等于 10、20、25 时的调用次数。把结果和第七节的斐波那契数据对比，说明为什么这两个数列的调用次数增长规律相同。
6. 把 `sum_list` 改写成循环版本（用一个累加变量），比较两个版本在列表长度为 1000 时的耗时和调用次数。然后尝试用递归处理长度为 2000 的列表，观察会发生什么，并记下报错信息。

**完成判据**：三个函数都跑通；调用树画出来了且与运行结果一致；第 3、5 步的表格有真实数字；第 6 步观察到了递归版本的报错，并能说出报错原因和解决办法（改成循环，或提高递归上限但说明其风险）。

**排查方法**：如果某个递归无限执行或者报 `RecursionError`，依次检查四点。第一，终止条件是否真的会被触发——比如写成 `if n == 0` 但递推让 $n$ 每次减 2，那么从奇数出发永远到不了 0。第二，规模是否真的在变小——递推里如果出现 `f(n)` 调用 `f(n)`，那就是无限递归。第三，是否在函数里修改了传进来的列表，导致后续判断出现意外结果；递归函数处理列表时尽量传切片或下标，不要就地修改。第四，可变默认参数是否被误用（`def f(a, memo={})`），这会导致多次调用之间互相污染。

## 常见误区

**误区一：“递归一定比循环慢，所以应该尽量用循环。”** 反例：第六章的归并排序用递归表达，复杂度 $O(n \log n)$，如果硬改成循环实现（自底向上归并），复杂度完全一样（常数上循环版甚至略快，但代码更难读也更难改对）。再比如第八章的树遍历，递归版本几行就写完，循环版本要自己维护显式栈。正确的判断是：**递归和循环的复杂度可能完全相同**，差别在常数开销和代码清晰度；只有当递归深度可能过大、或者每层递归都有隐含的复制代价（如示例三）时，才必须改成循环。

**误区二：“只要有递归，就一定要加记忆化。”** 反例：阶乘递归、欧几里得算法、归并排序，它们的子问题**互不重叠**，每个子问题只被求解一次，缓存没有任何收益，反而增加内存占用和一次字典查找的开销。记忆化只对**重叠子问题**有效——判断方法是画调用树，看有没有同一个参数的多次出现。

**误区三：“递归深度限制可以通过调高上限解决。”** 反例：把 `sys.setrecursionlimit(1000000)` 之后跑深度 10 万的递归，程序不会有 `RecursionError`，而是可能直接崩溃（段错误），因为操作系统为进程分配的栈空间是有限的，Python 只是提前检查了深度，并不能扩容真实的内存。正确的做法是把深递归改成循环或显式栈：深度与 $n$ 成正比的递归（如链表遍历、汉诺塔）都应当改写。

### Q02 · 单选题

下面这个函数的调用次数随 $n$ 的增长规律最接近：

```python
def f(n):
    if n <= 1:
        return 1
    return f(n - 1) + f(n - 2)
```

A. $O(n)$，因为每次递归只减少一点点规模
B. $O(n \log n)$，因为归并排序也是这个规律
C. 指数级，因为调用树中同一个子问题会被反复求解
D. $O(1)$，因为返回值是常数

### Q03 · 简答题

## 本章小结

- 递归由终止条件和递推关系两部分组成，缺一不可；规模必须确实在变小，终止条件要覆盖边界输入。
- 调用树是理解递归的主要工具：链式递归是一条链，分叉递归是一棵真正的树，重复节点暴露了重叠子问题。
- 朴素斐波那契的调用次数按 $1.618^n$ 增长，记忆化把它降到 $O(n)$；记忆化只对重叠子问题有效，并且要求函数是纯的。
- 递归有两个实际限制：深度上限和每层的常数开销。深度与 $n$ 成正比的递归应当改写成循环或显式栈；链式递归可以简单地换成循环，分叉递归需要自己维护栈。
- 下一章会进入树：树是递归最自然的用武之地，遍历、查找、插入都可以用几行递归写完，而树的形状又决定了递归的深度和整个操作的代价。
