# 排序算法

## 学习目标

- 能说明排序为什么是很多问题的前置步骤，并举出三个“先排序再处理”的实际场景。
- 能写出冒泡、选择、插入三种 $O(n^2)$ 排序和归并排序，并说明各自的工作方式。
- 能解释归并排序为什么是 $O(n \log n)$，以及为什么“比较排序不可能比 $O(n \log n)$ 更快”是一个有依据的界限。
- 能说出稳定排序的含义，并判断一个具体算法是否稳定。

## 开始之前

先修要求：会写嵌套循环、理解递归与函数调用（第七章会详细讲递归，本章的归并排序会先用一次）、能读懂 $O(n \log n)$ 这个记号。

热身问题：给你 8 张打乱的卡片，只允许比较两张卡片的大小然后交换它们，你估计最少要比较多少次才能排好？本章会给出这个问题的理论下界。

材料：Python 3.12 环境。本章有一段对比实验要真实运行。

## 情景导入

每学期的成绩单处理都会遇到同一件麻烦事：几百名学生的成绩需要按分数从高到低排列，同分的同学要保持原来的学号顺序。负责的同学先写了一个双重循环的排序程序，300 人时瞬间完成，他觉得没问题。第二年学生涨到 3000 人，程序跑了将近 10 秒；第三年涨到 30000 人，程序跑了十几分钟还没结束。

更麻烦的是同分处理：第一年的程序把同分学生的相对顺序打乱了，教务处要求同分时按学号排。他改了一版，在比较时加上“分数相同时比学号”，问题解决了，但程序更慢了。

后来他换成直接调用 Python 的 `sorted`，并传入一个排序键，30000 人不到半秒就跑完，同分顺序也对。

为什么自己写的排序在规模大起来之后会突然崩掉？为什么有时候“同分保持原顺序”是免费的，有时候又需要额外处理？本章会回答这两个问题，并说明“更好的排序”到底好在哪里。

## 知识讲解

### 排序为什么值得单独学一章

排序本身是为了让数据有序，但它的价值远不止于此。至少有四类问题会因为“数据已排序”而大幅变简单：

**第一，查找变快。** 第五章讲过，有序之后可以用二分查找把查找从 $O(n)$ 降到 $O(\log n)$。如果要做 $m$ 次查询，先花 $O(n \log n)$ 排序再查 $m$ 次，总代价是 $O(n \log n + m \log n)$；不排序直接线性查找是 $O(mn)$。当 $m$ 较大时，前者优势明显。

**第二，重复值变得相邻。** 判断有没有重复、统计每个值出现多少次、去重，都可以在排序后一趟扫描完成，不需要哈希表。这在内存受限或需要保证结果有序时非常有用。

**第三，许多算法以有序为前提。** 归并两个有序列表只需要 $O(n)$，而归并两个无序列表要先排序；区间合并、最大间隔、中位数查找等问题都有“先排序”的经典解法。

**第四，按序输出本身就是需求。** 成绩单、排行榜、日志按时间查看，最终产物就是有序的。

### 三种 $O(n^2)$ 排序：思路不同，代价相近

**冒泡排序**：重复地比较相邻两个元素，如果顺序不对就交换。每一轮结束，最大的元素会“浮”到末尾，所以下一轮可以减少一次比较。

```python
def bubble_sort(a):
    a = a[:]
    n = len(a)
    for i in range(n - 1):
        swapped = False
        for j in range(n - 1 - i):
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]
                swapped = True
        if not swapped:
            break
    return a
```

那个 `swapped` 标记很关键：如果某一轮里一次交换都没发生，说明数据已经有序，可以立刻结束。这个优化让冒泡排序在“数据本来就基本有序”时能快很多——对已经排好的数据，它只做一轮比较就退出。

**选择排序**：每一轮从未排序的部分里找出最小值，放到已排序部分的末尾。

```python
def selection_sort(a):
    a = a[:]
    n = len(a)
    for i in range(n - 1):
        m = i
        for j in range(i + 1, n):
            if a[j] < a[m]:
                m = j
        a[i], a[m] = a[m], a[i]
    return a
```

选择排序的特点是**交换次数最少**，每轮最多交换一次，总共不超过 $n-1$ 次。但它的比较次数固定是 $\frac{n(n-1)}{2}$，与数据是否有序无关——即使数据已经排好，它也要做完全部比较。

**插入排序**：像整理手里的扑克牌，把每张新牌插入到已排好部分中的正确位置。

```python
def insertion_sort(a):
    a = a[:]
    for i in range(1, len(a)):
        key = a[i]
        j = i - 1
        while j >= 0 and a[j] > key:
            a[j + 1] = a[j]
            j -= 1
        a[j + 1] = key
    return a
```

插入排序在数据**几乎有序**时非常快：内层循环的 `while` 条件在第一次比较就为假，每个元素只比一次，整体接近 $O(n)$。

下面这张表用实测数据展示三者在不同输入上的比较次数。数据规模 $n$ 分别取 5、10、20，输入分别是“完全逆序”和“已经有序”。

| $n$ | 冒泡（逆序） | 冒泡（有序） | 插入（逆序） | 插入（有序） |
| --- | --- | --- | --- | --- |
| 5 | 10 | 4 | 10 | 4 |
| 10 | 45 | 9 | 45 | 9 |
| 20 | 190 | 19 | 190 | 19 |

**读表要点。** 逆序时两者都是 $\frac{n(n-1)}{2}$ 次比较（$n$ 等于 20 时是 190 次）。有序时两者都降到了 $n-1$ 次（19 次），因为冒泡的 `swapped` 标记和外层循环条件都在第一次就结束，插入排序的内层 `while` 也在第一次比较就退出。这说明“$O(n^2)$ 的排序”在最有利的输入上可以表现得像线性——**复杂度说的是最坏情况的上界，不是每次都一定那么慢**。

### 归并排序：$O(n \log n)$ 的来源

归并排序的思路是分治：把列表一分为二，两边各自排好，再把两个有序的部分合并成一个有序的整体。

```python
def merge_sort(a):
    if len(a) <= 1:
        return a[:]
    mid = len(a) // 2
    left = merge_sort(a[:mid])
    right = merge_sort(a[mid:])
    out = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            out.append(left[i])
            i += 1
        else:
            out.append(right[j])
            j += 1
    out.extend(left[i:])
    out.extend(right[j:])
    return out
```

**为什么是 $O(n \log n)$。** 分两个层面看。第一，每次合并两个有序部分，需要把它们的所有元素都过一遍，代价与这一层元素总数成正比。第二，递归把数据对半分，一共分了 $\log_2 n$ 层（$n$ 等于 8 时是 3 层，$n$ 等于 1024 时是 10 层）。每一层的总代价都是 $O(n)$，乘上层数就是 $O(n \log n)$。

对比一下：$n$ 等于 1000000 时，$n^2$ 是 $10^{12}$，而 $n \log_2 n$ 约是 $2 \times 10^7$——相差五万倍。这就是为什么自己写的双重循环排序在几万个元素时就开始撑不住。

**为什么“比较排序不可能更快”有个界限。** 只用“比较两个元素大小”这一种手段来排序，$n$ 个元素的排列共有 $n!$ 种可能，而每次比较只能给出“是”或“否”两种结果。要做 $k$ 次比较区分 $n!$ 种情况，必须有 $2^k \ge n!$。由斯特林公式可以推出 $k \ge n \log_2 n - 1.44n$，也就是至少是 $\Omega(n \log n)$ 量级。归并排序达到了这个下界，所以在比较排序的范围内，它已经是最优的——不是“我们的实现还不够好”，而是**这类方法的极限就在这里**。

需要说明的是，这个下界只约束“通过比较来排序”的算法。如果元素是限定范围内的整数，可以用计数排序之类不依赖比较的方法做到 $O(n)$，但那已经不属于比较排序了。

### 稳定性：为什么它有时候免费，有时候不免费

**稳定排序**指的是：相等的元素在排序后保持它们原来的相对顺序。这在“先按一个字段排，再按另一个字段排”的场景里至关重要。

拿成绩单举例：先按学号排好，再用**稳定的**排序按分数排，那么分数相同的学生会保持学号顺序——一步就得到了“先按分数、同分按学号”的效果。

三种 $O(n^2)$ 排序的稳定性不同：

| 算法 | 是否稳定 | 原因 |
| --- | --- | --- |
| 冒泡排序 | 稳定 | 只在严格大于时交换，相等元素不会越过彼此 |
| 插入排序 | 稳定 | 内层条件是 `a[j] > key`（不是 `>=`），相等时停止移动 |
| 选择排序 | 不稳定 | 每次把最小值换到前面，可能把相等元素中的后者提前 |
| 归并排序 | 稳定 | 合并时条件是 `left[i] <= right[j]`，相等时优先取左边的 |

插入排序和归并排序的稳定性都落在那个 `>` 还是 `>=` 上。如果把归并排序的合并条件写成 `left[i] < right[j]`，它就不再稳定了——相等时优先取右边的元素，相对顺序被打乱。这是一个字符之差就改变性质的地方，改动后程序依然能排出正确结果，只是在“同分顺序”上悄悄出错。

Python 内置的 `sorted` 和 `list.sort` 都是**稳定**的，这一点写在官方文档里。这也是情景导入里“换成 `sorted` 之后同分顺序也对”的原因：他只需要按分数排序，学号顺序由稳定性自动保留。

## 详细示例

### 示例一：手算归并排序的合并步骤

任务：对 `[5, 2, 9, 1, 5, 6, 3]` 手工执行归并排序的前两层，写出每一步。

**第一层：拆分。** `[5, 2, 9, 1, 5, 6, 3]` 从中点分成 `[5, 2, 9]` 和 `[1, 5, 6, 3]`。继续分：`[5, 2, 9]` 分成 `[5]` 和 `[2, 9]`，`[2, 9]` 分成 `[2]` 和 `[9]`；`[1, 5, 6, 3]` 分成 `[1, 5]` 和 `[6, 3]`，各自再分成单元素。

**合并第一步：`[5]` 和 `[2, 9]`。** 先合并 `[2]` 和 `[9]`——两个都是单元素，比较 2 和 9，2 先出，得到 `[2, 9]`。再合并 `[5]` 和 `[2, 9]`：比较 5 和 2，2 先出；比较 5 和 9，5 先出；剩下 9。得到 `[2, 5, 9]`。

**合并第二步：`[1, 5]` 和 `[3, 6]`。** 先合并 `[1]` 和 `[5]`，得到 `[1, 5]`。再合并 `[6]` 和 `[3]`，得到 `[3, 6]`。然后合并 `[1, 5]` 和 `[3, 6]`：比较 1 和 3，1 先出；比较 5 和 3，3 先出；比较 5 和 6，5 先出；剩下 6。得到 `[1, 3, 5, 6]`。

**最终合并：`[2, 5, 9]` 和 `[1, 3, 5, 6]`。** 依次比较取小的：2 对 1 取 1；2 对 3 取 2；5 对 3 取 3；5 对 5 取左边的 5（因为条件写成 `<=`，相等时取左边）；9 对 5 取 5；9 对 6 取 6；只剩 9。最终得到 `[1, 2, 3, 5, 5, 6, 9]`。

**核对。**

```python
data = [5, 2, 9, 1, 5, 6, 3]
print(merge_sort(data))
print(data)
```

**预期输出。**

```text
[1, 2, 3, 5, 5, 6, 9]
[5, 2, 9, 1, 5, 6, 3]
```

第二行说明原始列表没有被修改——因为函数开头做了 `a = a[:]` 复制。

**为什么正确。** 两个有序序列合并的结果一定有序：每一步取出的都是两个序列剩余部分中最小的那个，所以输出序列天然非递减。这一步的代价与被合并的元素总数成正比，是合并过程 $O(n)$ 的依据。

**边界情况。** 两个 5 的相对顺序：原始数据里第一个 5 在原下标 0，第二个 5 在原下标 4。合并到最终结果时，因为相等时取左边的元素，下标 0 的那个 5 先被取出。这可以用带标记的数据验证：把 `[5, 2, 9, 1, 5, 6, 3]` 换成 `[(5,"A"), (2,"x"), (9,"y"), (1,"z"), (5,"B"), (6,"w"), (3,"v")]`，按第一个字段排序，结果中 A 应当排在 B 前面。**这是验证稳定性的标准做法**，值得实际动手做一次。

### 示例二：为什么自己写的排序会突然崩掉

任务：比较冒泡排序和归并排序在 $n$ 等于 500、1000、2000 时的耗时，观察增长倍数。

```python
import random, time

def bubble_sort(a):
    a = a[:]
    n = len(a)
    for i in range(n - 1):
        swapped = False
        for j in range(n - 1 - i):
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]
                swapped = True
        if not swapped:
            break
    return a

def merge_sort(a):
    if len(a) <= 1:
        return a[:]
    mid = len(a) // 2
    left = merge_sort(a[:mid])
    right = merge_sort(a[mid:])
    out = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out.extend(left[i:]); out.extend(right[j:])
    return out

random.seed(7)
for n in (500, 1000, 2000):
    d = [random.randint(0, 10 * n) for _ in range(n)]
    t0 = time.perf_counter(); bubble_sort(d); t1 = time.perf_counter()
    t2 = time.perf_counter(); merge_sort(d); t3 = time.perf_counter()
    print(n, round(t1 - t0, 4), round(t3 - t2, 4))
```

**推理过程。** 冒泡排序是 $O(n^2)$，$n$ 翻倍时耗时约翻 4 倍。归并排序是 $O(n \log n)$，$n$ 翻倍时耗时约翻 $2 \times \frac{\log(2n)}{\log n}$ 倍——对这个小规模而言接近 2 倍多一点。

**预期输出**（某次实测，列为 $n$、冒泡耗时、归并耗时）：

```text
500 0.0043 0.0004
1000 0.0175 0.0007
2000 0.0706 0.0014
```

**核对增长倍数。** 冒泡从 0.0043 到 0.0175 是约 4.1 倍，再到 0.0706 又是约 4.0 倍，与 $n^2$ 的预期吻合。归并从 0.0004 到 0.0007 是 1.75 倍，再到 0.0014 是 2 倍，与 $O(n \log n)$ 的预期吻合。这个实验把两个复杂度等级直接变成了可以观察的数字。

**边界情况。** 如果 `random` 没有设定种子，每次运行的耗时会有波动，但**增长的倍数**基本稳定——判断复杂度应该看倍数而不是看绝对值。另外要注意，这里的数据范围是 `0` 到 `10*n`，允许出现重复值（$n$ 等于 500 时范围是 0 到 5000，约有 10% 的元素会重复）。如果换成全部不同的数据，耗时几乎不变，因为比较排序的代价只取决于元素个数，不取决于元素的具体数值。

### 示例三：稳定性的一字之差

任务：验证归并排序中 `<=` 与 `<` 的差别。

```python
def merge_sort_stable(a):
    if len(a) <= 1:
        return a[:]
    mid = len(a) // 2
    left = merge_sort_stable(a[:mid])
    right = merge_sort_stable(a[mid:])
    out = []; i = j = 0
    while i < len(left) and j < len(right):
        if left[i][0] <= right[j][0]:       # 相等时取左边
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out.extend(left[i:]); out.extend(right[j:])
    return out

def merge_sort_unstable(a):
    if len(a) <= 1:
        return a[:]
    mid = len(a) // 2
    left = merge_sort_unstable(a[:mid])
    right = merge_sort_unstable(a[mid:])
    out = []; i = j = 0
    while i < len(left) and j < len(right):
        if left[i][0] < right[j][0]:        # 相等时取右边
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out.extend(left[i:]); out.extend(right[j:])
    return out

records = [(5, "A"), (2, "x"), (5, "B"), (1, "z"), (5, "C")]
print("稳定  ", merge_sort_stable(records))
print("不稳定", merge_sort_unstable(records))
```

**推理过程。** 两份代码唯一的差别是合并时用 `<=` 还是 `<`。稳定版本在分数相等时优先取左边序列的元素，而左边序列来自原列表的前半部分，所以原来的先后顺序被保留。

**预期输出。**

```text
稳定   [(1, 'z'), (2, 'x'), (5, 'A'), (5, 'B'), (5, 'C')]
不稳定 [(1, 'z'), (2, 'x'), (5, 'B'), (5, 'C'), (5, 'A')]
```

**核对。** 稳定版本里三个 5 按原顺序 A、B、C 排列。不稳定版本里 A 被挪到了最后——它原本在最前面，却排到了 B 和 C 之后。

**为什么这个差别重要。** 两份代码都能正确回答“谁分数高”，排序结果在“分数”这个维度上完全正确。差别只在同分学生的顺序上。如果程序接下来要把同分学生的排名视作并列，这个差别无害；如果接下来要把结果导出成成绩单发给家长，同分顺序错乱就会引起疑问。**稳定性是一种“额外保证”，不是正确性的一部分**，需求里没写清楚时很容易被忽略。

**边界情况。** 如果所有元素的分数都相同，稳定版本会返回原顺序，不稳定版本会打乱。这两种情况都“排对了”，但用途不同。还有一种更隐蔽的情况：如果排序键只包含部分字段，而记录的其他字段不同（比如此处姓名不同），不稳定排序会让输出看起来“随机”——这正是情景导入里教务处要求按学号排的原因。

## 动手实践

**目标**：自己实现冒泡、选择、插入、归并四种排序，用同一组测试数据和同一个验证函数检查它们的正确性与稳定性。

**材料**：Python 3.12 环境，`random` 模块。

**步骤**：

1. 实现四个排序函数，都在开头对输入做 `a = a[:]` 复制，不修改调用方的列表。
2. 写一个验证函数 `is_sorted(a)`，返回列表是否非递减；再写一个 `same_multiset(x, y)`，用排序后比较的方式确认两个列表的元素构成相同（不能只比长度，那样漏掉元素被替换的情况）。
3. 准备测试集，至少六组：空列表、单元素、两个元素（正序和逆序各一组）、含重复值、完全逆序、已经有序。对每组先用你预期的结果写下来，再运行四个函数，比对预期。
4. 验证稳定性：用 `[(分数, 标记)]` 形式的数据，让若干条记录分数相同，检查四个函数输出的相等分数中标记的顺序是否与输入一致。把四个结果整理成表格。
5. 用 `time.perf_counter()` 测量四种排序在 $n$ 等于 1000 和 2000 上的耗时，算出一倍规模时的增长倍数，填进表格。特别注意：测冒泡排序时 $n$ 不要太大（超过 5000 会明显变慢），否则会等很久。

**排查方法**：如果某个排序结果不正确，依次检查四点。第一，边界输入是不是没有处理——空列表和单元素列表最容易造成下标越界。第二，循环的上界有没有写成 `range(n)` 而不是 `range(n-1)`，后者会让内层的 `j + 1` 越界。第三，交换语句是否写成了 `a[j] = a[j+1]` 而漏掉反向赋值，那样会丢失元素（这一点可以用第 2 步的 `same_multiset` 立刻发现）。第四，归并排序的合并是否漏掉了最后 `extend` 剩余部分的那两行，那样结果会短一截。

## 常见误区

**误区一：“选一个复杂度最低的排序总是对的。”** 反例：数据只有 12 个元素，或者数据本来就几乎有序。归并排序虽然复杂度是 $O(n \log n)$，但它要额外分配列表、递归调用，常数开销较大；而插入排序在几乎有序的数据上接近 $O(n)$，且不需要额外内存。正确的做法是看数据规模和数据的初始有序程度，而不是只看复杂度等级。Python 内置的 `sorted` 用了 Timsort，它正是在小规模或部分有序时自动切换到插入排序。

**误区二：“排序之后原来的顺序信息就丢了。”** 不一定——如果算法是稳定的，相等元素的相对顺序会保留下来。这带来一个实用技巧：需要按多个字段排序时，不必写复杂的比较函数，只要**从次要字段到主要字段依次做稳定排序**即可。反过来，如果误用了不稳定排序，同样的写法就会产生错误结果，而且这个错误往往不会立刻显现。

**误区三：“只要结果是升序，排序就是对的。”** 反例：只要在合并收尾时漏掉一次 `extend`，结果就会少元素。比如把收尾写成只保留 `out.extend(left[i:])`，漏掉右边那份，那么对 `[5, 2, 9, 1, 5, 6, 3]` 排序会得到 `[1, 2, 5]`——它确实是升序的，长度却从 7 变成了 3。

```python
def merge_sort_drop(a):
    if len(a) <= 1:
        return a[:]
    mid = len(a) // 2
    left = merge_sort_drop(a[:mid])
    right = merge_sort_drop(a[mid:])
    out = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out.extend(left[i:])          # 漏掉了 right[j:]
    return out

print(merge_sort_drop([5, 2, 9, 1, 5, 6, 3]))
```

**预期输出。**

```text
[1, 2, 5]
```

这类 bug 的危险之处在于：**只检查“是否升序”的测试会放它过去**，因为 `[1, 2, 5]` 确实是升序的。必须同时检查元素构成（排序前后应当是同一组数）。

需要澄清一个容易搞错的地方：把两处 `extend` 的**顺序对调**并不会出错。因为合并的 `while` 循环结束时，两半中至多只有一半还有剩余元素，另一份必为空，交换顺序没有任何影响。这类“看起来可疑、实际无害”的写法不值得花时间去改，真正要防的是漏写、覆盖和下标偏移。

## 本章小结

- 排序是许多算法的前置步骤：它让查找可以用二分、让重复值相邻、让区间类问题可解，也常常是最终产物本身。
- 冒泡、选择、插入都是 $O(n^2)$，但行为不同：冒泡和插入在数据基本有序时接近线性，选择排序的比较次数固定与数据无关。
- 归并排序是 $O(n \log n)$，代价来自 $\log n$ 层的拆分与每层 $O(n)$ 的合并；比较排序的 $\Omega(n \log n)$ 下界说明这已经是这类方法的极限。
- 稳定性由比较条件里的 `<=` 还是 `<` 决定，一个字符就能改变性质；稳定性不是正确性的一部分，但它是“多字段排序”和“同分保序”能否成立的关键。
- 下一章会正式讲递归：归并排序已经用过它，但递归的代价、终止条件和递归深度对内存的影响还没有系统说明。
