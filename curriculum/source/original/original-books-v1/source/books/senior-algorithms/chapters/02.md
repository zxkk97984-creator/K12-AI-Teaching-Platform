# 数组和字符串

## 学习目标

- 能说明数组在内存中的存放方式，并据此解释“按下标访问是常数级”而“在中间插入是线性级”。
- 能写出字符串的常见处理：切片、查找、替换、反转、逐字符遍历，并说明各自复杂度。
- 能判断一段字符串处理代码是否会在循环里反复拼接，并改写成线性级写法。
- 能说出 Python 中字符串不可变带来的后果，以及列表为什么没有这个限制。

## 开始之前

先修要求：理解索引从 0 开始、会用切片、会写 `for` 循环、能读懂上一章的 $O$ 记号。

热身问题：一个列表有 100000 个元素，你执行 `a.insert(0, x)` 会在开头插一个元素。这个操作大概要移动多少个元素？如果改成 `a.append(x)`，要移动多少个？带着这两个数字进入本章。

材料：Python 3.12 环境。本章有一段对比实验需要实际运行。

## 情景导入

校园广播站的稿件系统出了一个问题。编辑把每篇稿件的正文当成一个字符串保存，程序需要做两件事：一是把文中所有“的的”改成“的”（编辑常打重复字），二是统计某个词出现了多少次。

第一版程序是这么写的：找到第一个“的的”，把它换掉，得到一个新字符串；再在新字符串里找下一个“的的”，再换掉……一篇 3000 字的稿子，程序跑了 12 秒。编辑以为电脑坏了。

后来有人把思路换成：先把正文按位置扫描一遍，记录所有需要修改的位置，最后一次性用 `join` 拼出结果。同一篇稿子，跑完不到 0.01 秒。

两者做的事情看起来一样，为什么差这么多？这和上一章的“复杂度”直接相关：第一版程序每一次修改都要把整个字符串复制一遍，$k$ 次修改就是 $k$ 次复制。本章会讲清楚字符串和数组在内存里究竟是怎么放的，以及这个存放方式带来了哪些必须记住的代价。

## 知识讲解

### 数组在内存里是怎样放的

数组（在 Python 里就是 `list`）在内存中占据一段**连续**的空间，元素一个挨着一个存放。每个元素占多少字节是固定的，于是“第 $i$ 个元素在哪里”可以由一个简单公式算出来：

$$\text{地址} = \text{起始地址} + i \times \text{单元素字节数}$$

这个公式里没有循环、没有查找，只有一次乘法和一次加法。这就是为什么按下标访问 `a[i]` 是 $O(1)$：不管 $i$ 是 0 还是 999999，计算地址的步骤数完全一样。

代价也随之而来。因为元素必须连续存放，一旦需要在中间插入一个元素，从插入位置往后的所有元素都得往后挪一格，给新元素腾位置——否则就不连续了。同理，删掉中间一个元素，后面的元素都要往前挪。移动 $k$ 个元素需要 $k$ 步，所以在开头插入或删除，最坏要移动 $n$ 个元素，是 $O(n)$。

对比一下两种插入：在末尾追加 `append`，因为后面没有别的元素要挪，所以平均是 $O(1)$（Python 的列表会预留一些额外空间，偶尔需要整体搬家，但摊到每次追加上仍然是常数）；在开头插入 `insert(0, x)`，要把全部 $n$ 个元素往后挪，是 $O(n)$。

这里有一个容易忽略的细节：Python 的 `list` 存的不是元素本身，而是指向元素的**引用**（可以理解为元素的地址）。所以“单元素字节数”是固定的（一个指针的大小），即使列表里装的是长度不同的字符串也不影响地址计算公式。这个设计让计算依旧是一次乘法加一次加法。

### 字符串：长得像数组，但不一样

字符串也可以用下标访问 `s[i]`，也可以切片 `s[1:4]`，看起来和列表很像。它们的共同点是都支持按下标随机访问，复杂度都是 $O(1)$。

关键差别在于**可变性**。列表是可变的：`a[0] = 5` 直接改掉那个位置的内容。字符串是不可变的：你无法在原地修改它，任何“修改”实际上都是创造了一个新字符串。

```python
s = "abc"
print(s[0])
# 下面这行会报错，字符串不支持按下标赋值
# s[0] = "x"

t = s + "d"
print(s, t)
```

**预期输出。**

```text
a
abc abcd
```

`s` 依然是 `"abc"`，`t` 是一个全新的字符串。这意味着 `s + "d"` 这一步要把 `"abc"` 的 3 个字符复制到新位置，再加上 `"d"`，总共复制 4 个字符。如果在一个循环里反复做 `s = s + ch`，第 1 次复制 1 个字符，第 2 次复制 2 个，第 3 次复制 3 个……第 $n$ 次复制 $n$ 个，总复制次数是：

$$1 + 2 + 3 + \cdots + n = \frac{n(n+1)}{2}$$

这是 $O(n^2)$。这就是情景导入里第一版程序慢的原因：它做了 3000 次左右的拼接，代价按平方增长。

### 常用的字符串与数组操作

下表列出高中阶段最常用的操作及其平均复杂度。记这些数字不是为了背，而是为了在写循环时能立刻意识到“这个操作放进循环里会不会出事”。

| 操作 | 写法 | 复杂度 | 备注 |
| --- | --- | --- | --- |
| 按下标取值 | `a[i]` | $O(1)$ | 列表和字符串都一样 |
| 取切片 | `a[i:j]` | $O(j-i)$ | 要复制出 $j-i$ 个元素 |
| 末尾追加 | `a.append(x)` | $O(1)$ | 摊还意义下 |
| 末尾弹出 | `a.pop()` | $O(1)$ | |
| 任意位置插入 | `a.insert(i, x)` | $O(n)$ | 后面的元素要挪 |
| 任意位置删除 | `a.pop(i)` | $O(n)$ | |
| 查找是否存在 | `x in a` | $O(n)$ | 逐个比较 |
| 求长度 | `len(a)` | $O(1)$ | 长度被单独记录 |
| 字符串相加 | `s + t` | $O(len(s)+len(t))$ | 生成新串 |
| 字符串连接 | `"".join(parts)` | $O(\text{总长})$ | 只复制一遍 |

最后一行是重点：`join` 会先算出总长度，一次性分配空间，然后把每一段复制过去，总共只复制一遍所有字符，所以是线性的。用 `join` 代替循环里的 `+=`，是 Python 里最常需要做的一处优化。

### 切片为什么不能随便用

切片很方便，但它会**复制**一份新数据。`a[:]` 看起来人畜无害，实际是把整个列表复制了一遍，是 $O(n)$。如果在循环里对每个元素都取一次长度为 $k$ 的切片，总代价是 $O(nk)$，当 $k$ 与 $n$ 同量级时就退化成了 $O(n^2)$。

```python
def all_pairs_naive(s):
    out = []
    n = len(s)
    for i in range(n):
        for j in range(i + 1, n + 1):
            out.append(s[i:j])
    return out

print(len(all_pairs_naive("abcd")))
```

这段代码枚举了所有子串，外层 $\frac{n(n+1)}{2}$ 个区间，每个区间切一次片，切片本身又是 $O(n)$，所以总代价是 $O(n^3)$。对 `"abcd"` 这种 $n$ 等于 4 的输入看不出问题，对长度为 1000 的字符串就会卡死。

**预期输出。**

```text
10
```

`"abcd"` 的非空子串个数是 $4+3+2+1 = 10$，和公式 $\frac{n(n+1)}{2}$ 在 $n$ 等于 4 时的结果 10 一致。这个核对很有用：它能同时验证你的计数公式和程序行为。

## 详细示例

### 示例一：统计词频，两种写法

任务：给定一个字符串，统计指定单词出现的次数（不区分大小写）。

```python
def count_word_slow(text, word):
    text = text.lower()
    word = word.lower()
    c = 0
    while word in text:
        c = c + 1
        text = text.replace(word, "", 1)  # 每次只替换一处
    return c

def count_word_fast(text, word):
    text = text.lower()
    word = word.lower()
    c = 0
    start = 0
    while True:
        pos = text.find(word, start)
        if pos == -1:
            break
        c = c + 1
        start = pos + 1  # 只往前推进，不重新复制整个字符串
    return c

sample = "the cat sat on the mat, and the hat"
print(count_word_slow(sample, "the"))
print(count_word_fast(sample, "the"))
```

**推理过程。** 两种做法的正确性都来自“找到一个就计数、然后从下一个位置继续找”。差别在代价：`count_word_slow` 每找到一处就做一次 `replace`，而 `replace` 会生成一个新字符串，复制了剩下所有字符；`count_word_fast` 只用 `start` 记录位置，`find` 在同一个字符串上往后找，不做任何复制。

设文本长度 $n$、出现次数 $k$。第一种最坏是 $O(kn)$；第二种是 $O(n)$（每次 `find` 从 `start` 开始，所有查找区间的总长度不超过 $n$）。

**预期输出。**

```text
3
3
```

**为什么正确。** 在样例中 “the” 出现在位置 0、13、29 附近，共 3 次。两个函数都返回 3，说明改写没有改变行为。

**边界情况。** 如果 `word` 是空字符串，两种写法都会陷入死循环或产生无意义的结果——`find("")` 总是返回当前位置，`start` 每次加 1 会一直找到末尾，返回 $n+1$ 个“匹配”。正确的处理是在函数开头判断 `if not word: return 0` 或者抛出异常。这是一类容易被忽略的边界：**空输入会让一些循环失去终止条件**。

### 示例二：反转字符串，以及一个不能想当然的地方

任务：把一个字符串反转。

```python
def reverse_slice(s):
    return s[::-1]

def reverse_manual(s):
    chars = []
    for i in range(len(s) - 1, -1, -1):
        chars.append(s[i])
    return "".join(chars)

s = "algorithm"
print(reverse_slice(s))
print(reverse_manual(s))
print(reverse_slice(""))
```

**推理过程。** `s[::-1]` 是切片，步长为 -1，一次遍历就得到结果，$O(n)$。手工版反过来遍历并把字符追加到列表，最后 `join`，也是 $O(n)$。两者复杂度相同，但切片版更短——这是“相同量级下选更简单的写法”的典型场合。

**预期输出。**

```text
mhtirogla
mhtirogla

```

**为什么正确。** 两种做法都恰好把每个字符放到对称的位置上。

**边界情况。** 空字符串反转的结果是空字符串，程序不会崩溃，输出一个空行。这是一个应当被验证而不是被假设的边界：如果程序改成 `s[0] + reverse(s[1:])` 这样的递归写法，空字符串就会在取 `s[0]` 时抛下标越界错误。同一个任务，不同的实现方式对边界的敏感程度完全不同。

### 示例三：一次拼接 vs 循环拼接

任务：把 10000 个单字符拼成一个字符串，比较两种做法。

```python
import time

n = 10000
parts = ["a"] * n

t0 = time.perf_counter()
s1 = ""
for ch in parts:
    s1 = s1 + ch
t1 = time.perf_counter()

t2 = time.perf_counter()
s2 = "".join(parts)
t3 = time.perf_counter()

print(len(s1), len(s2), s1 == s2)
print("循环拼接", round(t1 - t0, 4), "秒")
print("join  ", round(t3 - t2, 4), "秒")
```

**推理过程。** 第一段是 $O(n^2)$：第 $i$ 次拼接复制 $i$ 个字符，总复制量是 $\frac{n(n+1)}{2}$，$n$ 等于 10000 时约 5000 万次字符复制。第二段是 $O(n)$：一次算总长、一次分配、一遍复制。

**预期输出**（耗时数字随机器不同，此处为某次实测值，量级和比例才是重点）：

```text
10000 10000 True
循环拼接 0.0231 秒
join   0.0002 秒
```

**为什么正确。** `s1 == s2` 为 `True`，说明两种做法结果一致，差别只在代价。循环拼接比 `join` 慢了约两个数量级，换算成复制字符数，正好是 $\frac{n}{2}$ 倍的差距——这与理论分析吻合。

**边界情况。** 如果 `parts` 是空列表，循环版返回空字符串，`join` 版也返回空字符串，两者一致。但要注意 `"".join(parts)` 里的分隔符如果是 `","`，空列表会返回 `""` 而不是 `","`——连接符只在元素**之间**出现，不在末尾。这一点在生成 CSV 行时经常被弄错。

## 动手实践

**目标**：亲手测出“在列表开头插入”和“在末尾追加”的代价差距，并解释这个差距为什么随 $n$ 扩大而变大。

**材料**：Python 3.12 环境，`time` 模块（标准库，无需安装）。

**步骤**：

1. 写一个函数 `build_append(n)`，用 `for` 循环往空列表末尾 `append` $n$ 个元素，返回这个列表。
2. 写一个函数 `build_insert(n)`，用 `for` 循环往空列表的**开头** `insert(0, i)` $n$ 个元素，返回这个列表。
3. 分别取 $n$ 等于 2000、4000、8000、16000，对每个规模先各跑一次“热身”（不计时），再用 `time.perf_counter()` 计时三次取最小值，记录下来。
4. 把结果整理成一张表，四列分别是 $n$、`build_append` 耗时、`build_insert` 耗时、两者比值。
5. 观察规律：随着 $n$ 翻倍，`build_append` 的耗时大致怎么变？`build_insert` 的耗时大致怎么变？把观察写成一句话。
6. 用本章的内容解释第 5 步的现象：`insert(0, i)` 每次都要移动当前已有的全部元素，第 $i$ 次要移动 $i$ 个，总移动量是 $\frac{n(n+1)}{2}$；而 `append` 不需要移动任何元素。

**完成判据**：表格有 4 个规模、每格有真实数字；能写出比值随 $n$ 扩大的趋势（大致与 $n$ 成正比）；第 6 步的解释用到了“移动元素个数”这个说法，而不是“insert 比较慢”这种没有内容的结论。

**排查方法**：如果测出来的数字抖动很大，依次检查三点。第一，计时范围是不是只包住了函数调用，有没有把列表创建或其他准备工作算进去。第二，是不是只跑了一次——单次测量受系统调度影响很大，取三次最小值能明显稳定下来。第三，$n$ 是不是太小，$n$ 等于 2000 时 `build_insert` 也只有约 200 万次移动，和 Python 的解释器开销在一个量级上，建议从 4000 起测。

## 常见误区

**误区一：“字符串和列表差不多，能用的操作都通用。”** 反例：`s[0] = "x"` 对字符串会直接报 `TypeError`，对列表则是正常的赋值。原因是字符串不可变。这个差别带来一串连锁后果：字符串没有 `append`、没有 `pop`、没有 `sort`；想把一个字符串“改几个字符”，必须先转成列表、修改、再 `join` 回来。写代码时如果对一个字符串调用了列表的方法，多半就是踩了这个坑。

**误区二：“切片不花钱，反正看起来只是个冒号。”** 反例：`a[:]` 复制整个列表，`a[i:j]` 复制 $j-i$ 个元素。在循环里取切片尤其危险，示例三已经演示了 $O(n^3)$ 的可能。正确的理解是：切片产生的是**新对象**，代价与它的长度成正比。如果只是想遍历一部分元素而不需要新列表，可以用 `for i in range(lo, hi)` 直接按下标访问，避免复制。

**误区三：“`x in a` 很快，因为 Python 自带的方法都很优化。”** 对列表和字符串，`in` 是逐个比较，是 $O(n)$；对集合 `set` 和字典 `dict`，`in` 是基于哈希的，平均 $O(1)$。这两者的差距在循环里会被放大：一个 $O(n)$ 的循环里套一个 $O(n)$ 的 `in`，整体就是 $O(n^2)$。第四章会详细讲哈希，本章只需要记住判断依据是**容器的类型**，而不是操作符的样子。

- 说明你的做法在遇到空字符串、全由该标点组成的字符串、以及该标点出现在开头和结尾时分别会怎样，并实际运行验证。
- 如果稿件长度是 50 万字，你的做法的耗时大致随长度怎么增长？和“反复 replace”相比差多少？请给出估算理由。

## 本章小结

- 数组元素连续存放，地址可以由起始地址加下标乘元素大小一次算出，所以随机访问是 $O(1)$；也正因为连续，中间插入和删除要移动元素，是 $O(n)$。
- 字符串同样支持按下标访问和切片，但它不可变；任何“修改”都会生成新字符串，循环里反复拼接会退化成 $O(n^2)$。
- `join` 一次性分配并复制，是拼接大量片段的标准做法；切片会复制数据，在循环里用切片要特别小心。
- `in` 的代价取决于容器：列表和字符串是 $O(n)$，集合和字典平均是 $O(1)$，这为下一章的栈、队列和第四章的哈希结构埋下伏笔。
- 下一章会看到两种为“只在两端操作”而设计的容器：栈和队列，它们的代价分布与数组正好互补。
