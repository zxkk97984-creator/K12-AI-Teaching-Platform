数据库是有组织地存储大量结构化数据的系统。**关系型数据库**（MySQL、PostgreSQL、SQLite）用表存储，表由行和列组成，表与表之间用主键/外键关联。

SQL 是查询语言。最基础的：

```sql
SELECT name, age
FROM students
WHERE age >= 16 AND grade = 10
ORDER BY age DESC
LIMIT 10;
```

**JOIN** 把多张表按关联键拼起来：

```sql
SELECT s.name, c.course_name, sc.score
FROM students s
JOIN scores sc ON s.id = sc.student_id
JOIN courses c ON c.id = sc.course_id
WHERE c.course_name = 'Mathematics';
```

高中阶段不要求会建库调优，但要能读懂 SELECT、WHERE、JOIN、GROUP BY，理解"为什么要建索引"（没索引就是全表扫描 O(n)，有索引接近 O(log n)）。

再补充一个工程上的关键概念：**事务（transaction）**。转账时要从 A 扣钱、给 B 加钱，这两步要么都成功、要么都不做——不能扣了钱却没到账。事务靠 ACID 四个性质保证：原子性（不可分割）、一致性（数据库约束不被破坏）、隔离性（并发事务互不干扰）、持久性（提交后即使断电也不丢）。高中阶段能理解"为什么不能只跑两条 UPDATE 就完事"，就已经抓住了要害。

## 3.11 数据库深化

#### 3.11.1 GROUP BY 与聚合

```sql
SELECT class_id, AVG(score) AS avg_score, COUNT(*) AS n
FROM students
GROUP BY class_id
HAVING AVG(score) > 80;
```

`GROUP BY` 把行按某列分组，`COUNT/AVG/SUM/MAX/MIN` 是聚合函数，`HAVING` 对分组后的结果再筛选（区别于 WHERE 是分组前筛选）。

#### 3.11.2 索引是什么

索引就像书的目录：没有目录你要翻完整本书找一个词（全表扫描 O(n)），有目录直接翻到页码（B+ 树查找 O(log n)）。代价是索引占额外空间、写数据时要同步更新索引。所以索引不是越多越好，一般只给"经常出现在 WHERE/JOIN/ORDER BY 里的列"建索引。

#### 3.11.3 关系型 vs NoSQL

| 维度 | 关系型（MySQL/PG） | NoSQL（MongoDB/Redis） |
|---|---|---|
| 数据结构 | 严格表结构，schema 固定 | 文档/键值/图，schema 灵活 |
| 事务 | 强 ACID | 大多弱化事务 |
| 扩展 | 纵向为主（升配置） | 天然分布式横向扩展 |
| 场景 | 银行、订单、强一致 | 缓存、日志、社交动态 |

## 3.16 数据库设计深化

#### 3.16.1 ER 图概念

设计数据库前先画**实体关系图（ER 图）**：矩形表示实体（学生、课程），椭圆表示属性，菱形表示关系（选修），连线标注是一对一、一对多还是多对多。多对多关系要单独建一张中间表（如"成绩表"连接学生和课程）。

#### 3.16.2 范式直觉

- **第一范式**：每个单元格不可再分（不能在一格塞两个电话）。
- **第二范式**：每张表只描述一件事，非主键字段必须完全依赖整个主键（不能"课程名"依赖"课程号"却又塞进成绩表）。
- **第三范式**：非主键字段不能互相依赖（不能"系名"依赖"系号"，而系号又依赖学生号——系应该单独一张表）。

范式的目标是减少冗余、避免更新异常。高中阶段理解"一张表只管一件事"就够了。

#### 3.16.3 JOIN 类型

| JOIN 类型 | 含义 |
|---|---|
| INNER JOIN | 两表都匹配的行 |
| LEFT JOIN | 左表全部，右表没匹配补 NULL |
| RIGHT JOIN | 右表全部，左表没匹配补 NULL |
| FULL OUTER JOIN | 两边都保留 |

#### 3.16.4 索引原理

数据库索引通常用 **B+ 树**实现。它像一棵多叉平衡树，叶子节点存实际数据行（或指向数据行的指针），且叶子之间用链表相连——这让范围查询（"价格在 100 到 200 之间"）非常快。索引让查找从 O(n) 降到 O(log n)，但占空间、拖慢写入。经验：给高频 WHERE/JOIN/ORDER BY 列建索引，别给区分度低的列（如"性别"）建索引。

## 七、数据库 SQL 进阶

3.4 和 3.11 已经讲了基础 SELECT/JOIN/索引，这里再补几个高频进阶点。

### 7.1 子查询

把一个查询的结果当临时表用：

```sql
SELECT name, score
FROM students
WHERE score > (SELECT AVG(score) FROM students);
```

查出"分数高于全班平均分的学生"。

### 7.2 GROUP BY 与 HAVING

```sql
SELECT class_id, COUNT(*) AS n, AVG(score) AS avg_score
FROM scores
GROUP BY class_id
HAVING AVG(score) > 80;
```

WHERE 在分组前筛行，HAVING 在分组后筛组。

### 7.3 JOIN 类型实战

```sql
SELECT s.name, c.course_name, sc.score
FROM students s
INNER JOIN scores sc ON s.id = sc.student_id
LEFT JOIN courses c ON c.id = sc.course_id;
```

INNER JOIN 只保留两边都匹配的；LEFT JOIN 保留左表全部，右表没匹配补 NULL。

### 7.4 窗口函数概念

窗口函数可以在"不合并行"的前提下做聚合，比如给每个学生在班级内排名：

```sql
SELECT name, class_id, score,
       RANK() OVER (PARTITION BY class_id ORDER BY score DESC) AS rk
FROM scores;
```

这是高级 SQL 的分水岭，高中阶段了解概念即可。

### 7.5 索引为什么快

没索引时，查一个值要全表扫描 O(n)。建了 B+ 树索引后，树高通常只有 3–4 层，找一个值只需 3–4 次磁盘 IO，接近 O(log n)。但索引不是越多越好——每个索引都会拖慢 INSERT/UPDATE，因为索引也要同步更新。经验法则：给高频 WHERE/JOIN/ORDER BY 的列建索引。

### 7.6 事务 ACID

转账要从 A 扣 100、给 B 加 100，两步必须同时成功或同时失败。事务的四个性质：

- **A 原子性**：事务里的操作要么全做、要么全不做；
- **C 一致性**：事务前后数据库约束不被破坏（总分不能变负）；
- **I 隔离性**：并发事务互不干扰；
- **D 持久性**：提交后即使断电也不丢。

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

中间任何一步出错就 `ROLLBACK`，回滚到事务开始前。

## 3.6 信息安全与密码学基础

- **对称加密**：加密和解密用同一把密钥（如 AES）。速度快，但密钥怎么安全地送给对方是难题。
- **非对称加密**：一对密钥——公钥公开给别人加密，私钥自己留着解密（如 RSA）。解决了密钥分发问题，但慢。
- **哈希（Hash）**：把任意长度数据压成固定长度摘要（如 SHA-256），单向、雪崩（改一个字节全文大变）。用于校验文件完整性、存密码（存哈希而非明文）。

为什么网站存密码要存哈希而不是明文？因为一旦数据库泄露，用户的密码就全完了。存哈希的话，攻击者拿到的只是一串乱码，登录时把用户输入的密码算一遍哈希，和数据库里的比对即可。再进一步，还要给每个用户加一个随机的"盐（salt）"再哈希，防止两个相同密码的人在库里长得一样、防止攻击者预先算好彩虹表反查。
- **数字签名**：发送方用自己的私钥对消息哈希加密，接收方用发送方公钥解密验证——既证明"是他发的"，又证明"没被改过"。
- **HTTPS 的完整故事**：浏览器拿到服务器证书（由权威 CA 签发，证明这个域名确实属于这家公司）→ 用服务器公钥协商出一个对称会话密钥 → 之后所有数据用这个对称密钥加密传输。结合了非对称加密的安全握手和对称加密的速度。

为什么不全用非对称加密？因为 RSA 这类算法要做超大整数模幂，比 AES 慢两个数量级，拿它传整个网页你会等到怀疑人生。所以现实中的 TLS 是"混合战术"：握手阶段用非对称加密安全地交换一把临时对称密钥，之后所有数据都用这把对称密钥高速加密。这套设计兼顾了安全与性能，是现代互联网能够普及的关键工程决策。

## 3.12 密码学深入

#### 3.12.1 常见算法归类

- **对称加密**：DES（已不安全）、AES（现在的标准，128/256 位密钥）、SM4（国密）。
- **非对称加密**：RSA（基于大整数分解）、ECC（椭圆曲线，密钥更短）。
- **哈希函数**：MD5（已被碰撞攻破，不能用于安全场景）、SHA-1（同上）、SHA-256（目前安全）、SM3（国密）。

#### 3.12.2 数字签名完整流程

假设 Alice 要给 Bob 发一份合同，证明"这是我发的、没被改过"：

1. Alice 先把合同内容算 SHA-256，得到哈希 H；
2. Alice 用自己的**私钥**加密 H，得到签名 S；
3. Alice 把合同原文 + 签名 S 一起发给 Bob；
4. Bob 用 Alice 的**公钥**解密 S，得到 H；
5. Bob 自己对合同原文再算一次 SHA-256，得到 H'；
6. 如果 H == H'，说明合同确实是 Alice 发的、没被改过。

这里有个反直觉的点：**签名用私钥、加密用公钥**——别记反了。

## 3.17 密码学深入：证书与 HTTPS 握手全过程

#### 3.17.1 为什么需要证书

非对称加密解决了"密钥怎么安全交换"，但引入新问题：你怎么知道公钥真的是 `www.bank.com` 的，而不是中间人伪造的？**数字证书**就是答案：由权威第三方（CA，证书颁发机构）用它自己的私钥给网站公钥签名，证明"这个公钥确实属于这个域名"。浏览器预装了全球主要 CA 的公钥，所以能验证证书真伪。

#### 3.17.2 HTTPS 握手完整流程

1. 浏览器发 `ClientHello`：支持的 TLS 版本、加密套件、一个随机数；
2. 服务器回 `ServerHello`：选定的加密套件、另一个随机数、**服务器证书**；
3. 浏览器用 CA 公钥验证证书链，确认服务器身份；
4. 浏览器生成一个"预主密钥"，用服务器公钥加密发回去；
5. 双方用两个随机数 + 预主密钥各自算出同一个**会话密钥**（对称）；
6. 之后所有通信都用这个对称会话密钥加密。

整个握手只发生在建立连接时，之后对称加密飞快。这就是为什么你看到小锁时数据是安全的——除非你的电脑被人偷偷装了假根证书，那就是另一回事了。

#### 3.17.3 常见误区

- **"HTTPS 加速了网站"**：不，握手本身有开销，HTTPS 比 HTTP 略慢，但配合 HTTP/2、会话复用、CDN 后用户几乎无感。
- **"有 HTTPS 就绝对安全"**：HTTPS 只保护传输过程，不保护你电脑中毒、不保护你主动泄露密码、不保护钓鱼网站（钓鱼网站用的是真证书）。
- **"哈希是加密"**：不是。哈希单向不可逆，加密可逆。哈希用于校验和存密码，加密用于保密通信。

## 3.5 软件工程初步

一个软件项目不是写完代码就结束。**需求分析**搞清楚"到底要做什么"；**设计**决定模块怎么分、接口怎么定；**编码**实现；**测试**找 bug；**部署**上线；**维护**修复和迭代。常见模型有瀑布模型（按阶段线性推进）和敏捷开发（小步快跑、每周迭代）。

**Git** 是现代版本控制的事实标准。核心概念：仓库（repository）、提交（commit，一次快照）、分支（branch，平行开发线）、合并（merge）、远程仓库（GitHub/GitLab/Gitee）。常用命令：

```bash
git init
git add .
git commit -m "first commit"
git branch dev
git checkout dev
git merge main
git push origin main
```

学会用 Git 管理自己的作业和项目，是从"写脚本"走向"做工程"的分水岭。

Git 最反直觉的一点是：它记录的是**快照**而不是差异。每次 commit 都是当时整个项目的一个完整快照（没改的文件只存一个指针）。这让分支操作极其廉价——建分支只是写一个指向某个 commit 的指针，切换分支就是把指针挪一下。所以鼓励大家"大胆开分支"：想试新想法就建一个 `experiment` 分支，搞砸了直接删掉，主分支永远干净。

## 3.13 Git 分支模型

真实团队不会直接在 `main` 上干活。常见做法：

- `main`：永远可发布的稳定代码；
- `develop`：集成开发分支；
- `feature/xxx`：每个新功能开一个短期分支，做完合并回 develop；
- `hotfix/xxx`：线上出 bug 时从 main 拉一个紧急修复分支。

常用补充命令：

```bash
git status
git diff
git log --oneline --graph
git stash
git rebase main
git reset --hard HEAD~1
git reflog
```

`git stash` 把当前没提交的改动暂时藏起来，切分支干完活再 `git stash pop` 拿回来；`git reflog` 能找回"误删分支"——只要你 commit 过，几乎都能救回来。

## 3.15 Git 工作流深化

#### 3.15.1 merge vs rebase

把 `feature` 分支合回 `main` 有两种方式：

- `git merge main`：保留完整历史，生成一个"合并提交"，历史像树枝分叉。
- `git rebase main`：把 feature 分支的每个提交"摘下来"，重新接到 main 最新提交后面，历史变成一条直线。

rebase 历史干净，但**不要在已经推到远程的公共分支上 rebase**——因为它改写了提交历史，别人基于旧提交干活会冲突。黄金法则：**只 rebase 自己的私人分支，merge 公共分支**。

#### 3.15.2 解决冲突

两个人改了同一文件同一行，Git 不知道听谁的，会在文件里留下：

```
<<<<<<< HEAD
你的修改
=======
对方的修改
>>>>>>> branch-name
```

手动选择保留哪部分（或两者合并），删掉这些标记，再 `git add` + `git commit`。冲突不可怕，怕的是看见冲突就瞎选一边。

#### 3.15.3 .gitignore

有些文件不该进 Git：编译产物、`node_modules`、本地配置、密钥。在项目根目录建一个 `.gitignore` 文件，每行一个 glob 模式：

```
__pycache__/
*.pyc
.env
.idea/
dist/
```

## 3.7 计算机发展史

- **第一代（1940s–1950s）电子管时代**：ENIAC 用了一万八千个电子管，重 30 吨，耗电 150 千瓦，每秒只能做几千次加法。编程靠插线板。
- **第二代（1950s–1960s）晶体管时代**：晶体管取代电子管，更小、更省电、更可靠。IBM 7090 是代表。
- **第三代（1960s–1970s）集成电路（IC）时代**：把几十个晶体管刻在一块硅片上。
- **第四代（1970s 至今）超大规模集成电路（VLSI）**：一个芯片上塞几十亿个晶体管。1971 年 Intel 4004 只有 2300 个晶体管，2020 年代的 Apple M 系列已经上百亿。
- **摩尔定律**：Intel 创始人戈登·摩尔 1965 年预测——集成电路上晶体管数约每两年翻一倍。这条定律支撑了半个世纪的算力指数增长，但近年来因为物理极限（原子大小、散热、漏电）逐渐放缓，行业转向多核、专用芯片（GPU、TPU、NPU）。
- **GPU 的崛起**：GPU 本来是为游戏画面并行计算设计的，几千个小核心同时干活。深度学习刚好需要这种大规模矩阵乘法，于是 GPU 成了 AI 训练的标配——这是"无心插柳"的经典案例。

## 3.8 编程语言演化：为什么语言这么多

- **机器语言**：纯 0 和 1，人根本读不了，直接给 CPU 执行。
- **汇编语言**：给机器指令起助记符（`MOV`、`ADD`），但仍然和具体硬件强绑定。
- **高级语言（1950s 起）**：Fortran 做科学计算、COBOL 做商业数据、LISP 做人工智能。这一层让程序员不再关心具体硬件。
- **C 语言（1972）**：兼顾高级抽象和底层控制，Unix 内核就是 C 写的。直到今天操作系统、驱动、高性能库还是 C。
- **面向对象（1990s）**：C++、Java 把"对象"作为组织代码的核心单元，适合大型工程。
- **脚本语言（1990s–2000s）**：Python、Ruby 让"写脚本自动化"变得极快，不需要编译。
- **多范式与新语言**：Go（Google，为云原生设计）、Rust（内存安全、系统级）、Swift（苹果生态）。

为什么语言这么多？因为**没有"全能语言"**：写操作系统要 C/Rust，写数据科学要 Python，写前端要 JavaScript，写高性能服务要 Go/Rust。选语言就是在"性能、开发效率、生态、团队熟悉度"之间权衡。

## 3.14 计算思维与问题求解

最后回到方法论。计算机科学家解决问题的套路可以归纳为四点：

1. **分解（decomposition）**：把大问题拆成小问题；
2. **模式识别（pattern recognition）**：看看这个小问题像不像以前见过的；
3. **抽象（abstraction）**：忽略不重要的细节，只保留关键变量；
4. **算法（algorithm）**：设计一步步的解法。

遇到一个陌生题，别急着写代码。先花 5 分钟想：这个问题本质是什么？输入是什么、输出是什么？最小例子怎么解？暴力解法是什么？暴力解法哪里慢？能不能用哈希表、排序、DP、图把它加速？这套思路比背任何模板都重要。
